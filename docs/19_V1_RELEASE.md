# Agentic SDLC Starter v1.0

v1.0 is the first stable release boundary for this public starter.

It is not a claim of universal autonomous software development.

The release is valid only when the exact release commit passes:

```bash
python tools/verify_v1_release.py
```

and the repository CI is green on that same commit.

## Stable release properties

The starter provides a tested generic control architecture for:

- CLIENT/product authority separated from engineering execution;
- durable Product State and currentness;
- repository-first fresh-context reconstruction;
- canonical owner/supersession lineage;
- strategic Planner versus tactical Campaign Lead authority;
- persistent/resumable engineering campaigns;
- exact-candidate review and strategic terminals;
- state/DB/lineage/idempotency semantics;
- fail-closed multi-file control-state transactions and recovery;
- backward-compatible schema evolution;
- profile-proportional installation;
- read-only project discovery;
- explicit, preflighted, retry-idempotent adoption;
- physical stateful reference evidence;
- six-shape transfer/adoption tests;
- bounded governance and centralized control primitives.

## Release evidence

The machine-readable definition of done is:

```text
state/V1_RELEASE_CRITERIA.json
```

The executable release verifier covers:

1. structure/public boundary;
2. canonical contract instances;
3. validation falsification;
4. profile/scaffold transfer;
5. schema evolution;
6. canonical ownership;
7. fresh-context reconstruction;
8. physical stateful reference;

No one gate substitutes for another.

## Transfer claim

The starter has synthetic transfer evidence across:

- SMALL;
- STATEFUL;
- ARTIFACT_HEAVY;
- MULTI_WORKSTREAM;
- MULTI_PRODUCT;
- HIGH_CONSEQUENCE.

The tested adoption flow preserves application files, promotes control state transactionally, reconstructs without chat memory and keeps heavy mechanisms optional where they are not needed.

This is evidence of reusable starter mechanics, not proof that every arbitrary real repository can be adopted without project-specific work.

## Human / CLIENT boundary

v1.0 is designed so the CLIENT does not need to repair technical control state.

The CLIENT can still be required for genuine product authority, including:

- product-visible behavior;
- subjective/perceptual acceptance;
- material business or economic tradeoffs;
- publication, destructive or other external authority.

The architecture does not convert those decisions into engineering defaults.

## External systems and high-consequence work

The starter provides generic boundaries for security, privacy, rights, paid services, publication and destructive actions.

It does not certify a real project for security, privacy, legal compliance, rights clearance or production release.

Those gates remain project-specific and fail closed when materially unresolved.

## License boundary

This repository does not select an open-source license on behalf of the repository owner.

Public availability and technical forkability are separate from legal reuse rights.

A formal open-source license remains a repository-owner decision.

## Post-1.0 stopping rule

The starter architecture phase ends at v1.0.

Future architecture changes should be driven by concrete evidence such as:

- a reproducible adoption failure;
- a correctness or recovery defect;
- a compatibility/security issue;
- a generic failure class that existing mechanisms cannot represent.

Do not add new roles, policies, examples or versioned features merely to continue iteration.

Maintenance should prefer:

- defect repair;
- simplification;
- compatibility;
- evidence-driven hardening.

That is the intended stable-release posture.
