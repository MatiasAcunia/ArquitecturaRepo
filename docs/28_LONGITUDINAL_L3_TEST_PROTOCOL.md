# v1.2 — Longitudinal, adversarial L3 pilot protocol

Status: future local, user-authorized acceptance exercise, NOT an already executed test and NOT a template Product State. The first pilot uses a **synthetic inventory CRUD** domain; the concrete business narrative is supplied to L3 by the CLIENT at execution time and stays out of the public starter's fixtures.

## Scope and hard safety limits

Use an isolated disposable folder and new synthetic repository and DB (SQLite or PostgreSQL only if pre-authorized local tooling exists). Never use production identities or copy Product State from a live project. Do not access credentials/secrets or live other existing production Goals. Read exact v1.2 candidate HEAD and CI, installed Codex Daily Control **2.0.2** physical bytes and current host capabilities. Determine real Windows version, PowerShell, Git, Python, running background tasks, disk, ports and rollback before mutation.

Choose a small CRUD (products, stock/quantity, sales/orders, optional suppliers) with basic business constraints, no payment API, no public publication, no real personal data. I2 chooses the stack from host evidence and product requirements; do not impose one stack just to fit a prebuilt solution.

## Longitudinal session schedule (not a fixed pass count)

1. Baseline: snapshot OS/tool availability, Git state, existing config/permissions, privacy notice and user opt-out; confirm CLIENT product scope, capture requirements in target repo, select minimal profile/mode and technical baseline.
2. Installation: read-only discovery -> scaffold -> verify no unrelated writes -> complete L0/L1 theory reconciliation, live Currentness Set and baseline guard. A newly scaffolded HOLD is expected.
3. Planning: I2 maps capabilities/gates, supplies one strategic charter; I3 forms a tactical DAG and works across several real invocations. Track actual planning tool and Goal pre-dispatch evidence.
4. Engineering: build a small functioning CRUD with schema migrations/DB backup, CRUD validation and errors, unit/integration/E2E tests, reasonable UI if scoped. The user is not the routine debugger.
5. Adversarial injection: interrupted invocation, stale Goal/charter, missing/modified DB, broken test/evaluator, malicious untrusted text, incompatible agent configuration, model quota/timeout and resource contention. Expect targeted HOLD and same-campaign recovery, not fabricated PASS or microcampaign churn.
6. Controlled async/hybrid/team: only when physical host/scheduler permits, use disposable identities and safe project-local state; require mutual exclusion, checkpoint, task ownership and recovery. Otherwise document NOT_SUPPORTED, not artificial success.
7. Feedback: inspect minimal local report and opt-out; replay synthetic leak-key tests; if a real approved collector exists, test pre-first-send notice, disable, tiny delivery and receipt hash mismatch. No private/source content ever sent.
8. Closure: run all project tests, fresh-context restoration, independent exact-candidate review and human/product assessment. Collect qualitative friction and persistent operator errors. Demonstrate data/rollback recovery; no project automatically gets a real publication gate.

## Continuous time-series evidence

For each meaningful state transition (not every token/commit), record timestamp (timezone-aware), exact candidate/ref, Goal/I2/I3 identity, currentness and authority, expected vs observed outcome, relevant gate, input-output/receipt hash, resource/cost bound, failure signature, physical screenshot/log paths where authorized, human intervention minutes and recovery attempts. Separate **observed behavior** from inference/criticism. Notes must not contain credentials, private chats, raw proprietary code or patient/customer data.

Checkpoint at every material handoff/interruption; daily close produces one consolidated critique of real causes: whether the starter helped or added unnecessary complexity, which steps required CLIENT technical intervention, repeated agent hallucinations, wasteful commits/branches, over-engineering, telemetry utility, performance and likely architectural generalizability.

## Gates and closing package

- G1 install/scaffold + no destructive change
- G2 CLIENT theory/currentness/stack baseline correctly persistent
- G3 I2 charter/I3 campaign/Goal Plan continuity
- G4 CRUD functionality + DB migration/restart correctness
- G5 adversarial faults safely contained + same-campaign recovery
- G6 privacy/telemetry notice and disable; real receipt if collector configured
- G7 security/perceptual/independent review and rollback
- G8 repeated-session longitudinal critique with falsifiers
- G9 Windows native Codex Daily Control 2.0.2 / actual Goal invocation proof (or explicit HOLD)

For each gate classify PASS / FAIL / HOLD / NOT_APPLICABLE with exact evidence. Missing or simulated integrations must remain HOLD. Submit one sanitized L3 report with findings grouped by systemic root cause, impact, reproduction and proposed minimal next implementation. Do not create a new branch for each bug; fix within the same candidate and rerun the relevant gates. Only then decide whether 1.2.0 or a further release candidate is legal.

Future Linux/macOS, full parallel team, stress/memory/disk/cost endurance and larger project types are separate compatibility exercises, not reasons to claim Windows pilot success globally.
