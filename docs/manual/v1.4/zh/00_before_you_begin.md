## 1. 一个可以复用的工程组织起点

ArquitecturaRepo 是以 Git 仓库为中心的软件开发治理 starter。它提供职责与授权规则、可复制的模板、不同风险等级的配置、项目状态的组织方式、用于检查与恢复的 Python 工具，以及可选的参考运行机制。其目标是让新的开发者或新的代理会话能够从真实文件中恢复项目的当前状态，而不是要求用户复述之前所有聊天记录。

它不是自动生成完整应用的产品。安装后并不会自动知道你的用户是谁、数据库位于哪里、哪项功能已发布、哪项操作已获授权。真实项目仍然需要需求确认、编码、测试、运行、数据保护和必要的人类验收。仓库提供组织与验证这些工作的结构，而不是替代工作本身。

也不需要先订阅某种大型语言模型或云端接口。你可以由人类团队执行这些流程；如果选择接入编程代理，必须另外核对代理的工作目录、权限、成本与使用边界。拥有工具访问权限并不等于获得发布、消费预算或上传私人数据的许可。

版本边界尤其重要。v1.4.0 的发布标签关联固定的 ZIP 包、SHA-256 校验值和清单；随后添加到 main 分支的完整手册不能被当作已经存在于原先的 ZIP 中。使用者应明确区分“已发布且可复现的发行物”和“持续更新的文档”。[MIT 许可证](../../../../LICENSE)和[公开发布说明](../../../47_V1_4_RELEASE_NOTES_AND_UPGRADE.md)分别解释使用许可与版本范围。

## 2. 它比直接使用编程聊天更好吗

短小的实验里，直接告诉编程助手“写一个能够读取 CSV 的脚本”可能最快。你得到代码、运行一次、修改错误，任务就结束了。此时搭建复杂的治理层不一定有收益。我们不应仅凭文档页数或协议名称，就宣称 ArquitecturaRepo 在所有情况下更好。

但在需要持续数周、保存客户数据、多人参与的项目中，问题会不同。新的聊天可能不了解旧的决策；某次“测试通过”可能针对的是已经被改写的代码；开发者可能无法判断本次修改是否包括外部支付、生产数据库或公开发布。用户就不得不亲自调度技术细节、重复解释背景、区分哪些结果可信。

ArquitecturaRepo 希望把这些关系持久化：产品当前意图、批准的能力范围、负责任的角色、实际代码与数据库的标识、已运行的验证、仍然存在的风险、下一步被允许采取的行动。它把 Git、规范化的项目状态与检查工具结合起来，让对话不再是唯一的事实来源。

评价方法应该是实证的：相同需求下，初次交付需要多久？修改需求后是否还能保持正确？新的开发者能否安全继续？问题出现时需要用户亲自排查多少内部技术细节？最终产品是否真正可用？这些结果比工具数量更有说服力。该架构能够改善可追溯性，但自身也带来维护状态和流程的成本。

## 3. 角色与决定权

CLIENT 是产品意图的负责人。需要解决什么问题、服务哪些用户、优先交付什么、什么体验可以接受，以及哪些外部操作或费用获得批准，都由有权的产品方决定。CLIENT 不必亲自决定每个类的名称、数据库迁移细节或 Git 冲突的处理。

| 角色 | 主要责任 | 不应承担的事情 |
| --- | --- | --- |
| I1 Master Owner（需要时） | 多产品和共享资源的协调、系统性治理问题 | 为每个普通 bug 重建战略计划 |
| I2 Planner | 需求解释、技术策略、能力级计划、战略验收 | 把每次测试失败变成新项目 |
| I3 Execution Controller | 授权范围内的实现、调试、测试、恢复、复审和重做 | 擅自决定新的产品目标 |
| I4 专项执行者或评审者 | 有边界的实现、调查、独立核查 | 越过授权代表 CLIENT 决策 |

四类责任不意味着四个人或四个 AI 进程。小项目可由少数人承担多项责任；当评价需要独立性时，必须注意实施者与评审者的利益和判断是否足够独立。让相同的代码作者在另一个窗口里重复宣称 PASS，不等于独立审查。

Planner 设定能力的目的、范围和验收条件，获得授权之后由 I3 持续负责正常工程工作。普通的 bug、测试失败、内部重构与再次尝试，原则上在同一个 campaign 内解决。只有产品目标、授权边界或重要证据发生实质变化时，才重新讨论战略决定。

## 4. 事实的现在性与证据

真实的代码、运行配置、数据库、构建产物和验证结果，应当优先于旧报告和聊天总结。名为 CURRENT 的文件如果引用了已经不存在的提交，也不能因此自动成为真相。Git 提交的时间和作者信息同样不能单独证明当前的角色、授权或产品验收。

产品意图也会改变。如果 CLIENT 明确说“原来希望删除退出会员的记录，现在要保留付款历史”，新决策应更新当前需求，同时保留可追踪的历史。不能因为先前某段聊天写过另一种做法，就认定新决定无效。

当证据不足时，最安全的表达是“未验证”“不明确”“HOLD”，而不是填写虚构的成功标记。刚安装的控制层从 HOLD / UNTRUSTED_CONTEXT 开始，正是因为尚未核对真实项目的需求、代码、权限与状态。要解除这种不确定性，需调查并采用真实的基准，而非修改一个状态字符串。

如果数据库实际连接的是开发环境，而文档却称它为生产环境，不能继续执行依赖生产数据的操作。应先核对连接、状态和责任人。与此同时，与该不确定性无关的安全只读调查可以继续进行，不必把所有工作都永久停住。

## 5. 三个层面理解项目

可以把项目看作三个相互关联但不能混淆的层面。L0 是用户的表述和已确认的产品决定；L1 是整理成当前需求与 Product State 的产品模型；L2 是真实的代码、数据库、活动任务、测试和运行产物。

例如 L0 要求“保留每位会员的付款历史”。L1 应解释付款的含义、记录的生命周期以及可访问它的人。L2 则必须存在可靠的保存、查询和权限实现。仅仅在 L1 写了要求并不等于功能存在；L2 做出了某种保存功能，也不能自动证明满足 L0 的意图。

如果一个按钮显示“已支付”，需要问清楚它表示人工录入、外部服务确认，还是仅仅模拟的视觉效果。这三种情况的授权、风险、验收条件完全不同。软件可以在语法上正常运行，却在业务含义上完全错误。

新成员进入项目时，应当能够追踪三层之间的关系。只有聊天总结会丢失技术上的现在性；只有代码也未必能解释用户真正希望实现的结果。

## 6. 先采用适当的复杂度

架构的价值不是强制组建一个庞大的代理团队。一个简单的概念验证可以从 SMALL 配置开始；有持久会员信息的应用可考虑 STATEFUL；大量生成文件涉及来源和版权时可考虑 ARTIFACT_HEAVY。不同开发工作流协作、多个产品共享资源或高风险外部行为，对应其他配置。

先准备一张简短的产品说明：谁使用软件，最重要的操作是什么，要保存什么数据，运行在什么环境，第一版刻意不做什么，以及还有哪些问题未决定。这足以帮助 Planner 提出高价值的问题。用户不需要在开始时确定每个技术组件。

然后对真实代码和数据进行只读观察，建立可信的初始基准。首个交付可以很小，但应当是可运行、可验证、符合需求的真实能力。不要为了展示宏大结构而提前创建大量无人维护的状态文件。

## 8. 哪些事必须由用户决定

软件最终要服务的工作流程、重要的用户体验、数据保留和访问政策、预算、外部发布等，可能需要 CLIENT 或其他有权人员做决定。技术人员应把选择的影响说明清楚，但不能把权限不足包装成“已经默认同意”。

如果用户说“让注册界面更好用”，工程团队可以提供设计方案与测试，但必须让真实用户评价是否更容易操作。如果用户说“今天不要上线”，技术上的 release gate 即使通过，也不意味着可以擅自上线。

不需要为了每个内部技术错误都请求用户决策。实现者可以在授权范围内改进实现和测试。只有当产品含义、费用或外部风险变化时，再将需要用户决定的选项带回来。

## 9. 用会员管理系统贯穿学习

后续章节使用一个虚构的体育俱乐部。工作人员要登记会员、查询名单、记录会费；俱乐部负责人关心隐私和业务的连续性。第一个能力是会员登记与列表，第二个能力是人工录入会费记录。这些能力有依赖关系：会员标识必须可靠，才能将付款记录关联到正确的人。

我们不会假装已经开发出一个线上支付产品。案例只说明如何提问、安装、调查、授权、测试、发现问题、修复以及验收。真实项目需要真实的代码和用户反馈，才能证明功能已经存在。

## 10. 判断采用的实际收益

可以用两个规模相近的真实开发任务进行比较。记录从需求确认到可用版本的时间，后来修改需求所需的重做，跨会话交接时丢失的信息，问题出现时数据是否安全，以及用户是否必须亲自管理技术衔接。只有观察这些结果，才能判断治理层是否产生实际价值。

ArquitecturaRepo 适合强调长期连续性、责任边界和可恢复性的开发，但短期原型可能更适合直接编程聊天。让架构服务产品，而不是让产品成为架构的展示品。下一章从最容易出错的目录和版本问题开始，演示安全的安装路径。
