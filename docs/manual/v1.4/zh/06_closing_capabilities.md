# 06 — 能力验收与正确结束工作

ArquitecturaRepo · v1.4 完整用户手册 · 简体中文

> 一个工程任务报告“完成”，并不自动表示用户需要的能力可用。本章说明如何确定验收对象、区分不同验证关口、处理仍在原范围内的缺陷，以及形成可以让下一位工程师恢复的最终记录。

## 本章内容

1. 用户能力与代码任务的区别
2. 结束一项能力的五个要素

5. 验收、继续修复或改变目标
6. 防止永无止境的审查循环

8. 会员登记的实际判断练习

## 1. 能力是用户得到的结果

假设客户希望“前台工作人员能够登记新会员”。开发者编写了保存数据的函数，这是一项实现工作，却不代表完整的产品能力。工作人员还需要有合适的界面、权限、输入校验、可理解的反馈和可靠的数据保存。

一项能力可以很小。把“能登记并查询会员”做成可靠的第一版，之后再增加会费记录，通常比同时声称拥有登记、自动支付、会员卡和分析报表更容易验证。每项能力应有清楚的边界，用户才能知道自己现在真正能够使用什么。

内部代码质量也重要。合理的重构、消除重复和更好的测试可降低维护风险，但它们应服务于用户需求。数十个提交或大量文档并不能自动替代“会员真的能被正确保存和查询”。

## 2. 五个要素构成一次可信的结束

可以从五个角度评价一项能力：

| 要素 | 要回答的问题 |
| --- | --- |
| 产品目标 | 当前结果是否满足已批准的用户需求 |
| 准确候选 | 哪个代码、配置、DB 与产物组合被检查 |
| 验证证据 | 必要的单元、集成、数据和运行检查是否完成 |
| 人类判断 | 需要时是否由实际使用者确认体验 |
| 交接连续性 | 结果、限制和下一步能否从仓库恢复 |

每个项目不需要完全相同的复杂流程。简单的命令行工具可能不需要视觉设计验收；处理会员个人信息的应用则不能忽略访问权限与数据保存。选择与真实风险对应的关口，而不是为流程本身增加流程。

形式化的验收条件最好在 charter 获得授权时就已经定义。如果工作完成后才临时增加大量与目标无关的要求，容易造成永无止境的差错搜寻；反过来，如果当初定义的关键风险尚未验证，也不能因为进度压力就把它们隐藏。

## 3. 验收对象必须是同一个当前候选

假设昨天的候选 V3 在测试数据库中运行正常，今天的候选 V4 改动了用户权限和数据库迁移。不能只引用 V3 的测试报告就批准 V4。应记录需要重跑的测试和实际的当前对象。

代码哈希有助于识别实现，但还需要确定配置、数据库版本、相关资源与真实运行环境。某个截图可能来自旧代码，某个媒体产物可能被重新渲染，某个 CURRENT 文件可能指向已过期的版本。以精确的候选身份作为审查单位，才能避免不同版本的证据混合。

对数据库应用，尤其要检查“当前”是指开发环境、测试快照还是生产环境。开发快照里所有数据都一致，并不能单独证明生产 DB 已经适用。涉及外部服务时，还需要明确已调用的是模拟接口还是实际账户。

当候选发生改变，应基于影响范围决定需要重新验证哪些关口，而不是毫无证据地沿用全部旧 PASS。也不意味着每次修改都必须从头运行无关的大型测试；关键是让证据与改变后的对象保持对应。

## 4. 缺少证据不等于已经失败

如果单元测试通过，但没有任何实际页面操作记录，准确表述应是“单元检查通过，物理与人类体验未验证”。不能直接写“功能已全部完成”，也不能据此断定实际页面一定有故障。

缺少的检查属于原 charter 范围时，I3 应补充运行、记录或复查，并在同一 campaign 内提交新的候选。一次评审发现登记按钮失灵，或者 DB 校验脚本有 bug，不需要自动创建新的 Planner 项目。

需要区别三种情况：测试实际失败、测试尚未运行、测试曾运行但证据已经遗失。它们的恢复路线不同。测试失败要求修复原因；未运行要补充检查；证据遗失可能需要在相同条件下重新执行。只有真实记录支持的结论才应进入验收。

不过，若用户把原本只记录会费的功能改成从银行账户自动扣款，这是需求及外部风险的扩展。需要重新确认授权、费用和安全约束，不能当作普通的集成 bug 由 I3 自行决定。

## 5. 三种决策：接受、继续或重新定义

第一种是接受。当能力的实际用户路径符合产品目标，必要质量关口通过，版本与证据能被重建，相关人员已经确认使用体验和风险时，可以把能力记录为已验收。

第二种是继续在同一范围修复。如果仍有与原目标有关的 bug、性能问题、集成缺陷或明显的人类体验不一致，就把具体失败条件交回原来的执行过程。I3 应继续修复并重新验证，而不是让 CLIENT 不断批准内部修补计划。

第三种是重新定义目标。只有在用户明确提出新方向、现有范围变得不合适、重要新事实改变了系统性风险时，才需要 Planner 与适当授权者重新审视能力的边界。

这三种情况都应该记录清楚。不能因为一位评审者写了“PASS”就取代用户授权，也不能因为一个无关的格式警告就永久搁置已经满足目的的产品能力。

## 6. 反复返工需要正确的停止规则

真正影响用户能力的缺陷不能被数量众多的绿色测试掩盖。如果同一模块连续出现同一类型失败，I3 应检查整个问题子系统，而不是只在每次报告里增加一个针对最新症状的修补。

可以从依赖、错误路径、并发、状态变化、测试夹具、真实运行环境和可恢复性等角度展开系统性加固，并进行足够独立的复审。完成后交给 Planner 一份整合的终局结果，而不是几十份彼此替代的临时结论。

另一方面，也应知道何时结束。如果能力要求已经满足，实质性的风险得到处理，仍然存在的轻微问题有明确记录和负责人，那么可以决定接受并进入下一项工作。完美的幻想不能成为永远不交付的理由。

验收应说明已经测试的环境与范围，而不是承诺“世界上任何情况下都不会发生错误”。必要时通过有限用户、分阶段发布或回滚计划降低剩余风险，但发布本身仍要得到相应授权。

## 7. 把决定写入能被恢复的位置

最后的记录应包含：能力名称、对应的 charter、已验收的准确候选、验证结果与来源、批准者、仍然存在的限制、下一项能力的路线。把这些信息保存在项目的规范状态里，而不仅是某个聊天窗口的最后一条消息。

需要区分当前结果与历史。过去一次被拒绝的候选可以保留作为故障原因，但不应被误认为当前可发布版本。同样，曾经被接受的会员登记不能自动证明后来增加的会费功能也已通过验收。

下一位工程师应该能够独立找到正确的代码、数据库和所需证据，知道哪些能力已完成，哪些仍在进行，哪些操作尚未获批。这种可恢复性是长期项目的核心收益之一。

不要把接受记录无限复制到多个 CURRENT 文件。一个关切应有明确的规范所有者和当前表面。重复的“当前真相”越多，矛盾就越难发现。

## 8. 会员登记候选的验收练习

第一份候选实现了登记页面、API 和数据库写入。单元测试通过，但实际使用时工作人员连续两次点击保存，产生两名相同编号的会员。由于产品要求稳定、唯一的会员标识，此候选不能被接受。

I3 在原 campaign 中修复重复提交处理，并检查数据库约束、事务与并发情形。之后重新执行相关单元和集成测试，启动应用实际登记与刷新页面。还要验证无权限用户无法写入，以及保存失败不会破坏已有记录。

新候选表现正确后，前台工作人员仍发现成功提示不明显。工程团队改善操作反馈，再让实际使用者试用。当功能、数据安全与用户体验达到预先确认的条件，记录准确候选和证据，CLIENT 才能接受这一能力。

接下来开发会费记录时，不能引用“会员登记已通过”的结果声称支付系统也安全。新的能力需要其独立的范围、用户意义、数据关联与验收条件。对于任何真实在线支付，都还需要额外的授权与风控。
