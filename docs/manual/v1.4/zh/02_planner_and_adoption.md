# 02 — Planner、项目发现与正式接入

ArquitecturaRepo · v1.4 完整用户手册 · 简体中文

> 创建了 .agentic-sdlc/ 并不意味着项目已经被理解。真正的接入是将模板中的组织结构与实际产品的需求、代码、数据、权责和证据相连接。本章依据[接入与交接规则](../../../16_TRANSFER_ADOPTION.md)以及[产品发现说明](../../../21_PRODUCT_DISCOVERY_REQUIREMENTS_STACK_AND_DELIVERY.md)解释这一过程。

## 1. 聊天记录不是完整的项目

用户在第一次对话中可能说：“我需要一个系统登记俱乐部会员。”这句话说明了方向，但不足以确定全部操作、数据保存规则、访问权限或实际的实现情况。助手若立即创建大型代码库，很容易把猜测写成事实；如果以后用户更改要求，又可能出现多份彼此矛盾的状态说明。

首先必须分清哪些是客户表达的愿望，哪些是经过确认的产品决定，哪些只是设计建议，哪些确实存在于代码中。如果之前的聊天说“登记 API 已经完成”，却没有对应当前提交、配置和测试证据，不能把它当作已验证事实。

ArquitecturaRepo 的接入阶段正是为了避免这种混淆。HOLD / UNTRUSTED_CONTEXT 表示尚未证明模板的内容与真实项目一致。即使目录结构完好，仍需进行发现、确认、基准建立和可恢复性检查。将状态名称手动改成 READY，不会产生所缺少的事实。

## 2. 先调查工作空间，不急于写代码

Planner 应确认应用仓库的精确路径、当前分支、未提交变化、已有模块、数据库迁移和配置、测试入口以及可能运行的服务。最初尽可能使用只读方法，尤其是针对真实业务数据和既有治理状态的项目。

在已生成的项目控制层中，可使用下列工具辅助观察：

    & "python" ".agentic-sdlc\tools\project_status.py" --control-root ".agentic-sdlc"
    & "python" ".agentic-sdlc\tools\discover_project.py" --project-root "."
    & "python" ".agentic-sdlc\tools\reconstruct_context.py" --root ".agentic-sdlc"

这些命令能够展示文件与状态方面的线索，但不能替代对业务含义的理解。看到一个名为 members 的数据库表，不能确定它用于正式会员还是测试样本；找到一个付款函数，也不能证明它执行实际收款。

如果已有 .agentic-sdlc/，先检查它是否包含当前权责、活跃 campaign、持久状态与恢复记录。此时应使用[受治理项目的只读预检](../../../32_EXISTING_GOVERNED_ATTACHMENT.md)。不允许为了让当前教程“从头开始”而直接覆盖其他团队留下的控制信息。

调查需要区分开发与生产环境。一个在测试数据库中成功执行的查询，不等于生产数据库已经通过当前性检查。未经允许，不应在真实会员数据库中批量写入示例记录。

## 3. Planner 应问哪些问题

好的问题能够改变产品的行为，而不只是改变技术名词。例如“会员可以同时参加两种活动吗”会影响业务模型；“谁可以修改会费记录”会影响授权与审计；“退出俱乐部后是否保留历史”会影响数据生命周期。

| 需要确认的问题 | 对系统的影响 |
| --- | --- |
| 会员由谁登记和查询 | 用户角色及访问控制 |
| 同名会员如何区分 | 稳定标识与重复检查 |
| 活动与会员是什么关系 | 数据模型与列表呈现 |
| 会费“已支付”代表什么 | 人工记录或真实支付的区分 |
| 退出后是否保留记录 | 删除、保存期限与隐私 |
| 一开始不做哪些功能 | 第一个 campaign 的边界 |

CLIENT 负责决定业务意图。Planner 可以提出现实可行的选项与利弊，不应要求 CLIENT 指定每个类或索引。技术团队负责解释实现方式、性能与维护成本；如果这些选择会实质改变产品目标、隐私或支出，应把决定返回有权的人。

对于尚未得到回答的问题，记录为明确的不确定性。如果“删除会员”可能表示软删除、完全移除或仅隐藏，那么这几种操作对应不同的风险，不能任选一种并声称用户已经批准。

## 4. 建立真实的需求与技术基准

调查完成后，把已确认的需求与具体的技术证据相关联。技术证据包括源代码位置与版本、数据库结构与环境、当前配置、已执行的测试、已知故障、必要的运行产物。需要为每项重要能力说明：目前确实存在什么，尚未实现什么，哪些结果没有验证。

例如，会员列表页面已经实现，但新增会员只能通过直接修改数据库完成，那么“会员登记”这个能力仍然不完整。若注册 API 可以调用，但权限检查缺失，也不能直接认定真实的职员已具备安全的注册能力。

产品状态应使用明确的正本。决定的历史可以保留，但不要让两份文件同时声称自己是当前唯一的要求。Git 提交信息很有用，却无法单独证明用户验收、当前数据库的环境或者活动工作的责任人。每个关键事实都需要与其实际来源对应。

不必把项目所有未来想法一次性写进规范。先形成足够真实的初始模型，帮助下一位工程师识别正确目标和可安全行动的范围。过度详细、缺少证据的项目计划反而会产生虚假的确定性。

## 5. 从初始 HOLD 过渡到正式接入

接入可以理解为几个相互依赖的步骤。先观察真实应用与环境，再请 CLIENT 确认产品行为；之后确定技术基准、制定交付方向与接入说明，检查所有引用、责任与状态是否一致；最后将经过检查的状态正式写入规范位置，并重新验证可恢复性。

这一过程有专门的[接入与交接合同](../../../16_TRANSFER_ADOPTION.md)约束。不能通过虚构 JSON、随便填一个提交哈希、凭空给出批准记录来让验证器变绿。无法确认的关键事实应保留为 HOLD，直到合适的人员提供证据或决定。

正式接入不意味着所有产品功能都完成。它表示管理层已经能够可靠地指向真实的产品，知道它当前处于什么状态，并且能够定义后续授权工作的范围。刚安装、已接入、正在实现、已经验收是四个不同里程碑。

如果发现已有项目治理状态与新版本不兼容，应先做只读兼容性检查，明确需要迁移什么、保护什么和如何恢复。不能自动删除旧记录，也不能未经授权“用新模板重建”。

## 6. 让一个新会话证明可恢复性

接入是否有效，最好的问题是：一个完全没读过旧聊天的工程师，能否从仓库中知道当前的产品目标、代码和数据库基准、已批准的能力、正在执行的 campaign、必要证据与下一步责任人？

reconstruct_context 是检查这个条件的工具之一。它的输出还应与实际仓库和状态对照。如果引用指向不存在的文件、过期的版本或另一个环境，就需要修正真实的根因。

想象原先的 I3 进程中断，新的执行者接手。新执行者应该知道尚未授权上线、只能修改会员登记模块、最新候选的测试情况以及如何恢复，而不是从上一次聊天的最后一句话猜测。如果做不到，项目管理状态仍缺乏可恢复性。

被标注为 CURRENT 的文本也需要检查是否与物理证据相符；不能因为名称包含“当前”就免于核对。正确的优先级是实际代码、数据库、运行产物和已确认的产品状态高于二手总结。

## 7. 第一个能力如何获得授权

接入之后，Planner 不必同时规划整套俱乐部信息系统的全部内部任务。可以把第一个可用结果定义为：“具有适当权限的职员能登记新会员并在列表中看到保存结果。”

这一能力的边界包括必要的输入字段、稳定标识、重复检查、权限和数据持久性；可以明确不包含会费、支付服务和活动预约。然后记录对代码、数据库与其他模块的依赖，提出可验证的验收条件和失败条件。

获得授权的能力级 charter 交给 I3 Execution Controller。I3 负责在范围内进行编码、内部设计、调试、迁移、测试、独立审查与重试。一个普通 bug 不应迫使整个项目重新走一轮 Planner 战略评估。

当用户要求外部在线支付或公开发布时，目标可能超出原有范围，涉及新成本与安全问题；此时需要新的决策。但如果只是注册按钮不能显示、API 返回错误或测试脚本有缺陷，应在原有授权内修复。

## 8. 会员管理的初次接入示例

假设读取现有 club-app 后发现：数据库中已有一个实验性的会员表，代码里有查询接口，但没有面向职员的注册界面。旧聊天曾声称“登记完成”，然而没有找到对应的端到端测试。Planner 应如实记录现状，而不是复制之前的完成声明。

与 CLIENT 讨论后，初版要保存姓名、联系信息、活动类型和内部编号；未经许可不能公开联系信息。无需在线付款。Planner 将这些决定及其来源写入当前需求，并把技术现状映射到代码与数据库的真实标识。

第一个 charter 可以要求登记后能够立即在列表中确认会员、重复编号被拒绝、普通访客不能写入、错误不会破坏现有数据。实现者自行决定技术细节，必要时提出有成本和风险的备选方案。

首次候选可能 API 测试通过，但浏览器的列表并不刷新。I3 需要在原有 campaign 内排查原因、修复 UI 更新并重新执行相关测试。用户真实使用后仍觉得完成状态不明确，也可以通过人类评价反馈同一能力的缺陷。

只有当前候选的代码、环境、数据库与验证结果可追踪，并且相关人员确认需要的用户旅程真正可用，才能验收该能力。验收记录存放在规范位置，使未来的新会话可以独立理解。
