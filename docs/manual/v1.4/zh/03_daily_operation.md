# 03 — 日常运行：执行、测试与交接

## 1. 开始前恢复当前项目事实

新的工程会话应先查看正确的应用仓库、当前分支、未提交改动、Product State、已经批准的 charter、活动中的执行任务与相关证据。聊天历史可以提示之前遇到的问题，但不能替代物理文件、运行状态和当前版本的核对。

例如，昨天的报告称“注册页面测试通过”，今天的分支却包含了未经核对的 UI 变更。不能直接沿用旧结论。应确认测试对应的提交、配置、DB 和实际页面。如果同一工作目录里有其他人的未提交文件，先识别归属与用途，而不是为了得到干净状态就强制删除。

当来源互相矛盾时，先在只读模式调查差异。数据库不明的情况下，不允许执行依赖其状态的写操作；与问题无关的文档整理和本地安全测试则可能继续。正确的 HOLD 应有明确的范围和解除条件。

## 2. 一个能力应该有清楚的结果

用户说“把会籍管理做好”，含义仍然很宽泛。Planner 可以将首个能力限定为：“有权限的工作人员能够在网页上登记会员，看到保存后的列表，且不会因重复提交创建重复会员。”

定义范围时要写明输入、权限、数据保存、错误行为以及明确不包括的功能。例如实际收款、自动催缴、会员卡打印可暂时排除。这样工程团队能围绕一个完整的用户路径工作，而不是同时展开许多难以验收的支线。

能力级 charter 应说明为什么做、边界在哪里、依赖哪些系统、谁负责执行、如何验收、哪些现象足以否定完成。无需细化到“修改第几行代码”这种微型任务；内部实现路线应留给获得授权的工程负责人。

对简单产品，角色的数量也应保持适度。责任清楚比运行许多独立代理更有意义。如果同一人承担 Planner 与编码，需要特别留意重要验收时的独立性与利益冲突。

## 3. I3 对普通技术失败拥有连续责任

能力得到批准以后，I3 Execution Controller 负责实施、调试、重构、测试、恢复、评审协调和再次提交候选。数据库迁移在授权边界之内时，也属于这条工程链路。普通 bug 不应被当成新产品需求。

假设注册表单点击后页面不刷新。工程师应调查 API 返回、前端状态、缓存、数据库提交，修复根本原因并重新测试。无需要求 Planner 重新规划一个“修复刷新问题”的 campaign。若独立评审发现不符合原 charter 的问题，可把具体失败条件返回同一个执行链路。

如果同一类别的问题多次反复出现，不能无限追加局部修补和新编号。应系统性检查相关模块、依赖与测试方法，完成较全面的加固和独立审查。Planner 之后对合并后的终局结果进行战略性评价，而不是逐个批准每次内部调试。

但是，当工作需要连接真实支付网关、处理新的个人信息类型、改变部署方式或超出预设预算时，可能涉及产品与授权的实质改变。I3 不能仅凭现有 charter 自行扩大边界，应将具体影响提交到适当决策人。

## 4. 区分本地工程与敏感外部行为

读取代码、在授权目录中修改文件、执行本地单元测试，与向公网发布、使用付费接口、删除生产数据、把源代码发送第三方有不同的风险。后者必须明确目标、范围、权限和可恢复性。

一个已经登录的 GitHub 会话不等于获得对全部仓库的修改权。编程代理可以看到环境变量，也不意味着可以在回答中输出密钥。不得将客户数据、访问令牌、私人 URL 等复制到公开报告、问题单或本仓库。

对于自动化流程，先验证真实的运行边界。可选的参考 runtime 不保证原生 Codex Desktop、外部 AI 服务或第三方发布都已被测试。一次本地模拟成功，也不能成为对真实账户执行高风险操作的授权。

处理媒体和第三方依赖时，应满足实际适用的授权、隐私与许可证条件。缺少一张审计截图不自动证明素材违法；同样，有一个文件也不意味着已经取得全部权利。按真正的风险核实必要信息。

## 5. 如何判断执行报告有价值

“完成 120 个测试”可以说明检查量，却不能回答用户能否真的登记一位会员。应让报告围绕具体能力：当前候选是什么、相对原有需求增加了什么、哪些质量关口通过、哪些尚未验证、是否需要用户实际操作确认。

| 质量关口 | 核心问题 |
| --- | --- |
| Unit | 单个函数或规则是否正确 |
| Integration | API、数据库、界面是否能协作 |
| DB / Currentness | 检查对象是否是正确的当前数据与结构 |
| Semantic | 行为是否满足业务含义和异常情形 |
| Physical | 应用在实际环境里是否能启动和操作 |
| Perceptual / Human | 用户是否看得懂、用得顺手 |
| Release | 发行物、版本、发布权限是否正确 |

这些关口不能相互代替。绿色的单元测试不能证明网页已经打开；漂亮的演示也不能证明数据库安全；GitHub 上存在 ZIP 不代表它包含后续的文档改进。

审查应有合理的结束条件。真正影响能力的缺陷必须修复；与当前验收无关的微小警告不应导致无限期的战略停工。要让验收条件与实际风险决定投入，而不是通过不断制造审查轮次来衡量努力。

## 6. Git 和磁盘卫生也是工程连续性

Git 可帮助记录变化和准确引用代码，但提交本身不等于批准。一个分支的更新无法证明谁承担了工作、代码属于哪个 campaign、数据库对应哪个版本。重要决定仍需保存在合适的规范状态里。

多方同时开发时，按受影响的文件、数据库、服务和产物评估干扰，而不只是看它们是否属于不同项目。两个任务都修改相同配置就可能冲突；两个不同产品共享数据库资源也可能产生实际干扰。

通常只保留每个仓库一个持久工作副本。真正需要并发时，可暂时使用共享 Git 对象数据库的 worktree，完成后清理临时目录。大体积渲染、测试缓存、导出文件和中间产物应位于临时或被 Git 忽略的路径；只有必要的规范证据需要持久保存，并记录路径、哈希及来源。

“也许以后会用到”不足以成为无限复制仓库和产物的理由。磁盘耗尽会影响工程运行甚至恢复能力。清理时同样需要确定目标，不能误删当前的规范证据。

## 7. 每日结束时回答五个问题

结束一天之前，应当留下足够具体的信息，使新的会话能够继续。

1. 哪个用户能力取得了实际进展？
2. 证明这个进展的代码、配置、数据与产物分别是什么？
3. 哪些质量关口已经针对当前候选运行，哪些仍然未知？
4. 未解决问题的负责人是谁，是否仍属于原有授权？
5. 下一位工程师应从哪个规范文件与实际仓库位置开始？

不要把聊天的长篇逐字记录当成唯一的交接材料。只要用户意图、当前状态、技术证据和下一步路线能够从仓库恢复，就不需要重复过去几周的全部对话。

有时一天的主要成果是发现“之前以为有效的 DB 连接其实指向测试环境”。这种发现可能阻止了真实数据损坏，属于实质性的风险降低。与之相比，生成十份没有使用者的总结文件并不一定算进度。

## 8. 会员登记的一天

早上，Controller 读取会员登记 charter 与昨天的候选状态。当前 API 测试已经通过，但用户点击保存后看不到新会员。团队先确认候选的代码与数据库版本，重现故障并发现前端保留了旧列表。

工程人员修复状态更新，重新运行单元与集成测试，然后启动真实界面完成登记和刷新操作。测试还覆盖重复点击按钮、无权限用户和错误后原始数据不被覆盖的情况。所有操作都发生在获批范围内。

下午，俱乐部职员试用表单，认为“保存成功”提示不够明显。Controller 可以围绕原能力优化提示，不必再次请求 Planner 创建一个新项目。假如职员又要求直接扣取会员银行账户里的会费，这就是新的外部金融行为，需要单独讨论。

最后，团队将具体候选的标识、验证结果、剩余限制、下一次操作与责任人记录在规范位置。第二天一个新会话打开时，应能找到这些信息，而不是只看到一句“昨天都弄好了”。
