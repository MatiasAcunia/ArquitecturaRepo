# 04 — 提出变更请求与确定优先级

ArquitecturaRepo · v1.4 完整用户手册 · 简体中文

> CLIENT 的任务是明确想要的产品结果，而不是替执行团队管理所有代码细节。本章介绍如何提出可验证的变更、处理意见变化，并且区分普通实现错误与真正的新范围。

## 本章内容

1. 先说结果，不急着指定代码
2. 一份简明的变更说明
3. 用户的决定和技术团队的责任
4. 改变想法时如何保留历史
5. 质量和使用体验
6. 不要同时打开十项工作
7. 哪些问题必须获得明确批准
8. 良好请求的具体示例

## 1. 从用户遇到的问题出发

“帮我给数据库增加一个索引”可能是技术方案，但并没有完整描述产品需求。用户真正想要的也许是：“工作人员能在已有 500 位会员的列表中迅速找到指定的人，不用等待或翻动许多页面。”有了具体目标，技术团队才可以调查瓶颈是索引、查询、缓存还是界面设计。

提出变更时尽量回答四个问题：谁遇到了什么困难？在什么环境或操作下发生？理想情况下应该看到什么结果？有哪些不能被破坏的限制？不必写长篇技术文档，但需要给出足够具体的场景。

例如，前台工作人员需要通过姓名和会员编号查找记录。同名的两个人必须可区分；普通访客不应看到联系电话；退出俱乐部的会员应按照负责人确定的保留规则显示或隐藏。这些要求会影响产品的实际行为。

如果用户擅长编程，可以提出实现建议，但应与必须满足的产品结果分开。不要因为提议过一种技术方案，就不允许工程团队在有证据的情况下采用更安全、更简单的实现。

## 2. 一个可以直接使用的请求结构

不需要为每项需求新建复杂的战略文件。一份清楚的简明说明就足以启动调查。

| 项目 | 示例内容 |
| --- | --- |
| 目标 | 工作人员可以按姓名和编号搜索会员 |
| 使用者 | 俱乐部前台 |
| 当前问题 | 必须手动滚动很长的列表 |
| 期望结果 | 输入后显示匹配人，并能够识别同名会员 |
| 必须满足 | 无权限者不能看到私人联系方式 |
| 暂时不做 | 复杂统计和外部 CRM 同步 |
| 验收示例 | 两名同名会员可被正确区分 |
| 尚未决定 | 是否显示已退出俱乐部的会员 |

Planner 收到这份请求后，应检查当前应用、已批准的需求和正在进行的工作，判断是否可以并入原 charter，还是需要定义新的能力。只有影响真实产品方向的决定需要返回 CLIENT；测试脚本如何组织、使用哪种内部缓存则是工程工作。

“做得更专业一点”这种反馈并非没有价值，但要进一步描述具体问题。按钮不明显、输入错误后表单清空、移动端无法操作、页面加载慢，都可以转化为用户旅程和验收条件。

## 3. 不要让 CLIENT 管理工程细节

CLIENT 负责产品定位、业务规则、价值排序和敏感授权。I2 Planner 负责战略分析、范围和能力级验收；I3 Controller 负责持续实现、调试、重做和验证；I4 可承担有限任务与独立评审。多产品共享治理需要时可以设 I1。

假如一个表单保存时抛出异常，I3 应找到根本原因、修复代码和检查回归；不需要向用户询问“这个异常该由哪一位代理处理”。如果数据迁移在原 charter 范围之内，技术团队也需要负责迁移设计与恢复测试。

但如果产品方后来要求“把所有会员信息公开给其他俱乐部”，这不是普通的内部代码修改。它改变了个人数据的使用范围和权限，需要有权的人评估并决定。技术实现不应通过惯性扩大授权。

一个好的系统让用户可以专注于产品内容与体验，同时使每个技术环节都有明确负责人。流程数量本身没有价值；能够持续交付和安全恢复才有价值。

## 4. 改变主意是正常的，但历史不能消失

一开始，用户可能说“退出俱乐部的会员直接从系统删除”，后来又说“过去的会费记录必须保留，前台只是看不到退出者”。新的明确决定可以取代旧要求，但之前的设计和已有的数据不能被简单抹除。

新的决定需要进入当前需求的规范位置。旧决定保留为可追踪的历史，并标明已被替代；技术团队检查现有代码、数据库、备份及迁移是否受影响。如果已经执行过不可逆的删除，不能仅修改界面就声称所有历史恢复了。

如果多份文件都以 CURRENT 名义陈述不同规则，新工程师可能依据错误的一份继续开发。应找到适合每项状态的唯一规范位置，避免通过复制摘要制造另一套互相冲突的真相。

同样，不应该把某次 Git 提交当成完整的产品批准记录。实际的决定者、受影响的能力、实施结果和当前性仍需要可追踪的证据。

## 5. 质量与可用性也属于真实要求

“功能存在但用起来难受”是有效的反馈。假设前台工作人员能够登记会员，但在保存成功后不知道系统是否完成了操作，于是反复点击按钮并创建重复记录。这个问题可能同时涉及交互设计、接口处理和数据完整性。

技术团队要区分不同的验证。API 单元测试可以说明某种输入能被处理；浏览器操作可以证明页面真的工作；真实使用者的观察可以判断完成状态是否容易理解。这些关口不能相互替代。

反馈可以包括屏幕、设备、操作步骤、预期与实际结果，但不要直接公开包含真实会员私人信息的截图。若需要复现问题，可以用合成数据和脱敏的日志。

对于性能，也应尽量说明测试条件，而不是只说“快一些”。例如：在普通职员电脑上，查询一定规模的会员数据时界面应在合理时间内响应。具体指标需要依据真实用户环境确认；文档中的示例数值不是所有项目的强制标准。

## 6. 先完成有价值的能力

用户可能同时提出搜索、统计、支付、通知、会员卡、移动端和外部同步。没有必要立即将它们拆成七个并发的 campaign。应优先考虑阻碍当前使用者的关键路径、共享依赖、风险、成本和交付顺序。

例如先确保会员标识可靠，再开发会费关联。如果先做漂亮的会费报表，后来发现会员经常被错误合并，前期工作可能需要大量重做。优先级不仅由功能的表面吸引力决定，还取决于上游基础是否真实可用。

普通 bug 应在原有能力内修复。只有当用户确实改变目标、引入新风险或发现重大的战略证据时，才需要重新规划。不要为了提高“项目数”而让每次测试失败都变成新立项。

暂停某项工作时也要保留安全的停止点：当前候选、已实施变更、仍然存在的错误、需要恢复的环境和接手人。直接让新对话从零开始，会增加重复劳动与状态破坏的风险。

## 7. 真正需要明确批准的情况

“我们应该选择 PostgreSQL 还是 SQLite？”通常可以由技术人员根据并发、数据量、部署方式与成本提出建议。如果选择会显著影响产品预算或运维责任，可以让用户在清楚了解利弊后决定。

“能否把会员资料上传第三方？”“能否删除生产数据库里的旧记录？”“能否订阅付费 API 并开始扣费？”则直接涉及隐私、资金或不可逆操作。执行前需核对正确的授权者、范围和后果，不能把工具可用性当成许可。

如果某个决定仍未明确，受其影响的外部行为应当 HOLD。但是不依赖该决定的代码调查、原型演示或安全的本地测试，仍然可以继续。好的边界是停止有风险的部分，而不是让所有工程无意义地停摆。

## 8. 五份具体可执行的产品请求

以下示例都以产品结果为核心，并且留出了实现者的技术空间。

1. “我希望前台能通过姓名和会员编号搜索，结果要区分同名会员，未授权用户不显示联系电话。”
2. “保存新会员后要有清楚的确认提示；表单校验失败时，不要丢失用户已经输入的内容。”
3. “让我查看本月尚未缴纳会费的人员；第一版只记录人工收款，不连接在线支付平台。”
4. “会员登记页面在手机上也必须可操作，关键按钮的位置和提示应让实际工作人员试用后确定。”
5. “旧会员数据迁移到新结构时不能丢失，迁移之前需要验证备份和恢复方法。”

这些说明还不是最终工程 charter，但足以让 Planner 开始调查和分解。如果用户只说“全部使用 AI 自动化”，首先应问清楚哪一步需要自动化、是否涉及个人数据与外部服务、错误会产生什么影响、怎样判断自动化确实有帮助。

如果已完成的候选被用户拒绝，应具体指出与原有目的不一致的行为，交由 I3 在同一范围修复。若拒绝的原因是用户现在想要完全不同的产品，那才是新的战略议题。正确区分两者，既保护用户的决策权，也避免技术团队反复重开工作。
