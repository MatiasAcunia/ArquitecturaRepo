# 05 — 发生故障后的诊断与安全恢复

ArquitecturaRepo · v1.4 完整用户手册 · 简体中文

> 真正的恢复不只是让测试重新显示绿色，而是找出原因、保护现有数据和证据，并在明确的范围内证明问题得到解决。本章区分环境失败、控制层错误、真实产品故障与敏感操作。

## 1. 先保护证据，再改变系统

遇到失败时不要立即删除缓存、重建整个仓库或强制覆盖数据库。首先记录实际发生的现象、发生时间、执行操作、受影响的用户、当前代码与配置标识，以及合理可用的错误日志。必要时保留输入条件和可以复现问题的步骤。

如果日志包含会员姓名、联系方式、访问令牌等敏感信息，不要为了求助直接贴到公共聊天或 issue。可以通过合成数据重现问题，或者只记录经过适当隐藏的技术细节。保留证据不等于无限复制私人数据。

接着确认受影响的环境。是开发机上的验证脚本失败，还是生产系统无法登记会员？是一个页面问题，还是数据库可能损坏？恢复行动的优先级取决于真实风险。特别是当前生产数据不明的时候，不应让自动化程序未经授权进行破坏性写入。

对已有活动 campaign 的项目，还需要确认未提交的代码、当前执行租约、数据引用和最后可靠的候选。把这些记录删掉，可能使唯一的恢复路径消失。仅凭旧聊天说“之前已经备份”不足以证明备份仍然存在且可用。

## 2. 本地环境和服务连接失败

Python 不存在、jsonschema 未安装、工作目录错误、Git 凭据失效、网络服务暂时不可用，都可能导致检查失败。这类错误与产品需求本身正确与否不相同。

可以先在 PowerShell 中执行：

    & "python" --version
    & "git" status --short
    Get-Location

如果缺少验证依赖，从安装的控制层所附的 requirements-validation.txt 中安装。不要修改检查器的预期结果来掩盖本地环境问题。也不要因 GitHub 暂时无法访问，就把本地仓库里的文件视为已经成功公开合并。

当代理连接到错误的仓库时，应立即停止写入，检查工作目录、目标分支、凭据的作用范围。具有登录会话并不代表获得跨仓库授权。如果问题涉及账户验证，应通过正规的登录和权限管理方式处理，切勿在聊天中索取或展示秘密信息。

## 3. 控制层未通过验证的正确解释

控制层检查可能报告缺少文件、无效的 JSON、引用断裂、状态矛盾、无效的权限或 CURRENT 与实际代码不一致。首先区分格式问题、环境问题、真实缺失的证据和某个验证器本身的错误。

首次生成的 .agentic-sdlc/ 返回 HOLD / UNTRUSTED_CONTEXT，可能是预期中的结果。它告诉你项目尚未完成正式接入，不应为了让仪表板变绿而填入虚构的当前提交、产品要求或验收记录。

如果测试器对一个真实有效的用例错误地报告失败，则需要检查协议和验证实现是否一致。这个技术问题可由 I3 在已授权的 campaign 内修复、复测并进行独立检查。无需每发现一个测试器 bug 就向 Planner 发起新的战略循环。

但如果真实数据库的版本无法确认，或者代码引用已经过期，仅修改测试器不能解决问题。必须重新核对代码、数据库、配置和当前状态之间的关系。证据缺失应被明确记录，直到找到可信依据。

## 4. Git 不能代替数据库恢复

有人看到测试失败后，可能想用强制 reset、删除目录、重新 clone 解决问题。这些操作有时会不可逆地丢失尚未提交的工作、审查证据或活动中的状态。执行之前必须确认确切目标、变更的归属和可恢复性。

Git 可以记录代码变化，却不能自动撤销生产数据库写入、支付服务调用或外部文件发布。即使把代码恢复到上周版本，如果上周之后的会员记录已经被删除，数据也不一定会回来。

涉及数据库迁移的恢复需要同时检查模式、数据、备份、迁移日志和应用的读写兼容性。在隔离环境中测试恢复方案，确认关键记录之间的关系，再由有权的运维人员决定是否在真实环境执行。

有些问题可通过保留现有改动、修复一个文件和重新测试来解决。不要为了简单的拼写或编译错误而创建额外的完整仓库副本。恢复动作越接近真实问题，越容易解释和审查。

## 5. 重复出现的错误意味着需要改进方法

一次页面刷新失败可以由 I3 修复并重新验证。但如果相同模块连续多次返工，不能继续只增加局部判断和“修复第八轮”的文档。需要调查系统性原因：状态更新机制是否设计不当、API 契约是否含糊、测试是否根本没有覆盖实际页面、数据库环境是否经常混淆。

在这些情况下，I3 应针对整个相关子系统开展更完整的加固，检查依赖、异常路径、状态变化、并发条件与恢复方式，并且让独立评审者审视实现者的假设。完成之前，不应反复把短暂的测试绿色称为最终完成。

普通重做仍属于原有授权的工程工作。Planner 的下一次主要介入应是对已经整合的战略结果进行验收，而不是为每个小错误创建新 charter。只有当业务目标或实际风险条件发生重大变化时，才需要新的战略决定。

## 6. 敏感信息、访问控制和素材权利

故障调查常涉及日志、截图和数据导出。对于会员管理软件，这些材料可能含有真实的个人信息。调查只应收集必要范围，避免把完整客户数据库或私人聊天复制到公共仓库。访问令牌如有泄漏风险，应由有权的人员按照实际环境的安全程序轮换或撤销。

第三方图片、视频、字体和软件库的使用，需要遵守适用的许可与授权。不能把“评审报告还没有附上许可截图”等同于“该素材一定禁止使用”，也不能仅因为素材能下载就认定可以无限制分发。应核对实际限制并保存必要来源。

本 starter 的反馈系统也有明确的隐私边界。v1.4 默认允许在采用者项目里产生最小化的本地元数据报告；是否周期性运行与是否向外部收集者发送，是不同配置。使用 --no-feedback-workflow 只处理调度，若要完全关闭生成器，应核对配置中的 enabled=false。[反馈隐私文档](../../../22_PRIVACY_PRESERVING_ARCHITECTURE_FEEDBACK.md)说明这些区别。

连接任何外部 AI 或存储服务并不是故障修复的必需步骤。没有明确授权时，不应把私人代码或数据库导出给新的第三方。可以先利用本地检查、现有源代码和允许的工具进行诊断。

## 7. 怎样确认故障已经真正结束

恢复报告至少应当回答：故障的真实原因是什么？哪些代码、配置或数据发生了变化？问题是否在原条件下可重新验证？针对当前候选运行了哪些测试？是否已经检查了实际的产品操作？仍有什么风险？

不同的质量关口要分开报告。一个函数测试通过不等于 API 与 DB 集成正确；数据保存成功不等于页面可操作；开发环境正常也不等于生产环境已验证。需要时还应记录人工体验、隐私、安全和发布授权。

结束并不意味着证明世上所有情况都不会出错。应以与功能风险相称的检查为依据，说明测试覆盖的设备、数据和环境。对不影响当前验收的微小问题，可以公开记录并安排后续处理，而不必让项目无限停滞。

最后，把根因、修复、当前候选、验证、尚未完成的事项和下一个负责人写到可恢复的规范位置。一个新的会话应该能够理解障碍如何得到解决，而不是重新依赖原工程师的记忆。

## 8. 三个恢复场景

### 场景 A：新项目安装成功但仍然 HOLD

俱乐部项目刚生成 .agentic-sdlc/，状态报告指出真实需求、代码基准与所有者尚未采用。正确做法是继续项目发现和正式接入，而不是手动把状态改为 READY。

如果管理员为了让检查通过填写一个不存在的提交哈希，后续执行者就可能在错误的代码基础上继续工作。这个场景中的 HOLD 是有价值的保护，而不是需要隐藏的失败。

### 场景 B：页面显示“成功”，刷新后会员消失

前端表单展示成功信息，但重新打开列表找不到新会员。单元测试可能全部通过，因为它们没有检查真实的数据保存路径。I3 应调查接口返回、事务提交、连接的数据库和前端缓存，确认每一步是否指向相同的环境。

修复后在安全测试数据上完成注册、刷新、再次查询及错误恢复。若属于原本的会员登记能力，不需要新的 campaign。当前测试所对应的提交和数据库环境应被记录。

### 场景 C：一次迁移导致部分会费记录消失

发现历史会费缺失时，先停止可能扩大损害的写入，检查可用备份和迁移日志，比较当前数据与可恢复的基准。代码回退不能自动恢复缺失的数据。

若授权允许，可在隔离环境中验证备份是否完整，确认每笔会费仍对应正确的会员与月份。真正向生产环境恢复前，应评估停机、数据冲突、受影响人员和回滚方案。

恢复后检查的不只是“总金额看起来正确”，还应包括明细记录与关联关系。只有实际数据完整性被合理验证，才能说明恢复达到了目标。
