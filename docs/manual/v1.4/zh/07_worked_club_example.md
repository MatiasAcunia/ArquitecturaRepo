# 07 — 完整示例：俱乐部会员和会费管理

ArquitecturaRepo · v1.4 完整用户手册 · 简体中文

> 最后一章通过一个虚构的体育俱乐部，把用户初次表达需求、仓库安装、真实项目接入、授权的实现、反复修复、人工验收和最终交接联系起来。请注意：这是可复用的教学案例，不是已经发布的真实应用。

1. 俱乐部的真实问题是什么

## 1. 一个规模不大但有实际风险的产品

假设一个社区体育俱乐部有前台工作人员、负责人和多种活动。当前成员信息散落在纸质记录与表格中。工作人员希望能快速登记新会员、找到现有会员、查询参加的活动，并查看会费情况。

对这个问题，第一反应可能是构建一套包含在线支付、会员卡、自动发送通知、复杂报表和智能预测的大平台。但用户眼下最需要的，可能只是可靠的会员登记和手动会费记录。提前扩展会增加开发与验收成本，也可能引入未得到授权的外部数据服务。

因此先确认两个能力。第一项让有权限的职员登记并查询会员；第二项让职员为已登记会员录入会费支付记录并查询未缴情况。本案例不执行真正的在线扣款，也不自动公开任何私人数据。

因为系统要持久保存姓名、联系方式和缴费历史，可以选择 STATEFUL 配置。这个选择意味着需要认真考虑数据一致性与恢复，但不会自动证明数据库已有备份，也不强制建立一个庞大的代理组织。

## 2. 先让 CLIENT 确认业务含义

Planner 不应从“会员管理”四个字自动推导所有细节。至少需要确认会员如何唯一识别、谁可以登记和编辑、会籍退出如何处理、每项活动是否可能有不同费用、会费缴纳记录与真实银行交易是否关联。

| 事项 | 本案例的教学假设 |
| --- | --- |
| 会员标识 | 每位会员有稳定且唯一的内部编号 |
| 必需信息 | 姓名、联系方式、活动类型 |
| 操作者 | 有授权的前台职员 |
| 可见性 | 未经许可不显示私人联系方式 |
| 退出会员 | 保留历史的具体期限仍需确认 |
| 会费 | 手动记录收到款项，不发起银行交易 |
| 首版排除 | 在线支付、CRM 同步、自动通知、复杂分析 |

实际部署时，这些假设必须由真正的俱乐部负责人确认。尤其是删除与保留历史的规则，不能由工程师根据方便程度擅自决定。没有得到回答的部分可以暂时标记为未定，并避免执行依赖该决定的不可逆行为。

优先解决哪些问题也由产品价值决定。若人员根本无法准确登记会员，那么先开发漂亮的财务图表不能解决核心困难。需求应尽可能反映使用者完成工作的顺序。

## 3. 在正确的目录进行安装

开发者把公开的 ArquitecturaRepo starter 与实际的 club-app 分开。需要复现发行内容时，从[固定的 v1.4.0 Release](https://github.com/MatiasAcunia/ArquitecturaRepo/releases/tag/v1.4.0)取得 ZIP 并核对 SHA-256。持续变化的 main 分支包含发行后的文档，不等于过去的发行包。

在确认目标目录是全新、且没有现有 .agentic-sdlc/ 后，可以从 starter 的目录运行示例命令：

    & "python" "tools\scaffold_project.py" --target "..\club-app" --profile "STATEFUL" --product-id "CLUB_MANAGER" --objective "Club member and dues records" --language "en" --no-feedback-workflow

目标目录、ID 和说明应换成实际项目的信息。如果 club-app 已经具有治理状态，应该转向[已有项目的只读接入预检](../../../32_EXISTING_GOVERNED_ATTACHMENT.md)，而不是强制覆盖。

生成后检查实际应用是否还完整，运行必要的状态工具：

    & "python" ".agentic-sdlc\tools\project_status.py" --control-root ".agentic-sdlc"
    & "python" ".agentic-sdlc\tools\discover_project.py" --project-root "."
    & "python" ".agentic-sdlc\tools\reconstruct_context.py" --root ".agentic-sdlc"

最初显示 HOLD / UNTRUSTED_CONTEXT 不代表工作失败。这个结果提醒我们：模板无法凭空知道真实产品的代码、DB、需求和授权。接下来仍需要 Planner 进行调查与正式接入。

## 4. 从试验代码建立真实的基准

假设 club-app 中已经有一个试验性会员表，支持按 ID 查询，但没有可供职员使用的登记表单。旧聊天提到“登记功能已完成”，可是在当前仓库里没有对应页面和最新测试。Planner 应相信实际代码与运行证据，而不是旧报告。

先以只读方式确认数据库环境、表结构、现有 API、代码提交、活动分支以及可能尚未提交的改动。对于真正的会员数据，必须避免未经授权的修改与导出。找到真实证据后，将其与 CLIENT 已确认的产品意图对应起来。

在[接入与交接规则](../../../16_TRANSFER_ADOPTION.md)下，Planner 建立清楚的需求、当前技术基准和责任边界。采用规范化的状态记录，而不是把合成样例中不存在的提交哈希和“测试通过”声明复制过来。

接入完成的意义是：新工程师能够知道真实项目位于哪里、产品要做什么、目前已经实现什么以及下一项授权工作是什么。它尚未等于登记功能已经完成。

## 5. 第一项能力：登记与查看会员

Planner 将最初的能力定义为：有权限的职员输入姓名、联系方式和活动类型，保存会员记录，并在列表中看到结果。相同编号不可重复；错误发生时不会损坏已有会员；无权限的普通访客不能登记。

需要的依赖包括会员 ID 的规则、数据库保存、API 与界面之间的协议、访问控制以及最基本的异常处理。故意排除会费与支付，有助于让能力清楚且可验证。

授权的 charter 描述目标、范围、依赖、责任人、验收条件和失败条件。它不需要指定每个类与实现步骤。I3 Execution Controller 接手后，负责内部技术方案、实现、测试、调试、恢复和独立复审。

如果工程团队使用临时模拟数据做演示，应明确这一点。不能把演示页面与实际有持久保存功能的产品混为一谈。完成代码编写只是第一步，后面还需要多层验证。

## 6. 第一份候选为什么还不能验收

假设第一个候选 API 测试通过，保存后返回正常状态，但职员在网页上看不到刚刚登记的会员。开发者可能觉得“后端已经完成”，然而用户需要的是完整的登记路径。对于这个能力，实际界面不刷新是实质性缺陷。

I3 调查前端状态、接口响应、缓存和数据库连接，在原 campaign 中修复。修复后重新运行单元、集成与浏览器测试，检查保存后列表更新以及重新打开系统后数据是否还在。

第二个问题是按钮连续点击两次会创建重复会员。Controller 应调查接口幂等性、数据库唯一约束与并发请求，而不是只依靠前端阻止第二次点击。对真实业务而言，重复会员可能使后续会费错配，因此属于必须验证的行为。

第三个问题来自职员的实际体验：界面虽然正确保存，但成功提示不明显。工程团队应听取用户反馈，改善操作提示。这是对人类使用质量的检查，不能被单元测试自动取代。

如果这些问题都属于原授权的登记能力，就应在同一 campaign 内修复、整合和复审。无需让 Planner 针对每次 bug 重新设计整个产品。只有业务边界真的改变时才要重新决定。

## 7. 第一项能力验收后才继续会费

针对当前准确候选，技术团队验证权限、数据保存、重复处理、实际页面操作，职员也确认可以理解并使用。然后在规范位置记录已经验收的代码和配置、相关 DB 证据、实际测试、批准者、剩余限制及下一步工作。

接下来 Planner 定义第二项能力：工作人员可以为会员录入某月的会费支付记录，并查询未缴情况。它依赖第一项能力的稳定会员 ID。如果会员可以被错误合并或随意重用编号，账目会与错误的人关联。

要再次确认会费周期、金额、补缴、作废、退款或更正的业务含义，以及谁有权限修改旧记录。这里仍然只做人工会费记录，不代表已经连接银行或支付平台。

第二项能力需要自己的测试：同一个月重复录入、错误的会员编号、权限不足、网络失败后重试、月份边界、数据持久性，以及历史记录不能被意外覆盖。第一项能力的“登记通过”不能替代这些会费相关的验证。

如果后来用户希望真正在线收款，需要考虑合同、资金流、隐私、外部成本和事故恢复。这是产品范围的重大变化，应先获得适当授权，而不是由 I3 在原有的手动记录 charter 中自行添加。

## 8. 把缺陷交给正确的工程负责人

假设会费记录候选在测试 DB 成功，但实际界面把上个月的未缴名单显示为本月。首先应核对日期与时区规则、查询过滤、缓存、数据基准和实际使用情形。这个问题在已授权的会费记录能力之内，I3 应继续处理。

若同一类日期错误反复出现，团队不应只修补某个条件分支。应系统审查时间和月份的业务定义、数据库字段、测试夹具、不同的边界日期与真实查询路径，再让独立评审者检查。没有重要的新战略证据时，不需要创建多个替代性 campaign。

反过来，如果调查发现实际俱乐部属于多个国家，须支持不同货币与不同财务规则，原有设计的业务范围可能已经不适合。这属于会改变系统重要约束的新事实，应提交 Planner 与 CLIENT 重新确认。

每次结果都要说明准确的代码、数据库和环境。来自演示数据的 PASS 不代表生产数据的当前性已经核对；来自旧候选的截图也不代表当前的界面仍然正确。

## 9. 用一个全新会话进行验收演习

假设最初的所有聊天都不可用。打开同一仓库的新工程师应该能够回答以下问题：

1. 俱乐部软件当前为哪些人服务，CLIENT 批准了什么目标？
2. 会员登记能力已经验收的是哪个具体候选？
3. 会费记录能力处于未开始、进行中还是已验收状态？
4. 当前代码、数据库、配置和验证证据分别在哪里？
5. 哪些问题仍然属于已批准的 I3 工作，谁负责继续？
6. 哪些行为，如在线付款与公开发布，尚未获得授权？

如果无法回答，就说明仍缺乏可信的交接信息。应补齐正确的规范记录、修复断开的引用、核对当前技术来源，而不是让新的代理通过猜测填补空白。

最后，可以把这个开发过程与直接在编程聊天中开发相比较。ArquitecturaRepo 并不保证短期原型更快，但如果它让需求变化、跨会话恢复、错误复查与真实验收更可靠，并减少用户亲自组织技术工作的负担，就产生了可测量的价值。
