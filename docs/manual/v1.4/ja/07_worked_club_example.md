# 07 — 実践例：小さなクラブ管理アプリを構築する

ArquitecturaRepo · 完全ユーザーマニュアル · v1.4版 · 日本語

## 1. 架空のクラブの問題を定義する

地域の小さなスポーツクラブを考えます。受付の職員は紙や表計算ソフトで会員を管理しており、名前の検索、活動区分の確認、月ごとの会費記録に時間がかかっています。クラブの責任者は「登録、一覧、会費の状況を一つの画面で確認したい」と希望しています。

ここで最初から、オンライン決済、顔認識、AIによる会員予測、外部の会計システム連携を追加する必要はありません。初版では会員を登録・検索でき、会費を記録として扱える小さなアプリケーションを目標とします。実決済はしないという境界を明示します。

関係者は、受付職員、クラブ責任者、会員自身です。誰がデータを閲覧し、修正し、削除する権限を持つかは製品判断です。保存する情報に名前や連絡先が含まれるため、プライバシーと権限が重要です。永続データを持つという理由から、導入時のプロファイルはSTATEFULを検討できます。

「会員管理アプリが完成した」という結果はまだ存在しません。ここであるのは、依頼者の希望と仮の要件だけです。次の段階で、実際の既存コードと利用者の意思を確認します。

## 2. 仕様を決める質問をする

Plannerは、会員の識別方法、活動区分、退会、会費の意味、利用者権限を確認します。たとえば「同じ名字の会員が複数いるときどう区別するか」という質問がなければ、一覧画面だけを作っても誤った会員を編集してしまう可能性があります。

もう一つ重要なのは、「会費を支払った」と表示する条件です。現金を受付が受け取った事実を職員が記録するだけなのか、オンライン決済プロバイダへ送金するのかでは、必要な契約、技術的保証、セキュリティが異なります。今回は前者だけを対象にします。

| 要件 | 初版での確認例 |
| --- | --- |
| 会員の識別 | 一意の識別番号を使用する |
| 登録項目 | 氏名、連絡先、活動区分 |
| 重複の扱い | 同じ識別番号を二重に登録しない |
| 権限 | 受付職員は登録できるが、一般閲覧者はできない |
| 退会 | 履歴を残すか正式な運用者に確認 |
| 会費 | 支払記録の入力に限定し、決済実行はしない |
| 初版の除外 | 外部同期、自動請求、複雑な統計 |

これらはシナリオを進めるための仮の判断です。現実のクラブへ導入するなら、実際の担当者に確認しなければなりません。製品の意図を決めるのはCLIENTであり、技術担当が便宜上勝手に確定するものではありません。

## 3. スターターを正しい場所へ導入する

開発者はArquitecturaRepoを入手し、アプリケーション本体のリポジトリとは分離します。すでに管理層があるなら[既存プロジェクトの接続手順](../../../32_EXISTING_GOVERNED_ATTACHMENT.md)を確認します。新しいプロジェクトでは、対象を点検してからスターターのルートで次の例に相当するコマンドを実行します。

    & "python" "tools\scaffold_project.py" --target "..\club-app" --profile "STATEFUL" --product-id "CLUB_MANAGER" --objective "Club member and dues records" --language "en" --no-feedback-workflow

その後、対象のclub-appに生成された .agentic-sdlc/ を確認し、検証用依存関係を導入して次の調査を実行します。

    & "python" ".agentic-sdlc\tools\project_status.py" --control-root ".agentic-sdlc"
    & "python" ".agentic-sdlc\tools\discover_project.py" --project-root "."
    & "python" ".agentic-sdlc\tools\reconstruct_context.py" --root ".agentic-sdlc"

HOLD / UNTRUSTED_CONTEXTが返されても正常な場合があります。この時点では実際のクラブのコード基準、DB状態、採用済み要求がまだ確認されていないためです。生成された管理ファイルが存在するという事実と、実製品が採用済みであるという主張を区別します。

## 4. 採用のための技術調査

仮に対象アプリケーションへ、会員テーブルの試作と一覧を表示するコードがすでに存在するとします。Plannerはそれを読み取り専用で調査し、どの機能が本当に実装済みか、どのテストが実行可能か、どこにDBとそのマイグレーションがあるかを確認します。

チャットに「登録機能はほぼ完成」と書かれていても、その表現をコードの現在性へ置き換えません。実際のソース参照、設定、スキーマ、必要なデータの基準点を確認します。テストが実行されていなければ未検証とします。担当者や以前の作業の権限が不明なら、確かめるまで書き込みを行いません。

次に、利用者が確認した要求と技術的な基準点を管理層の適切な正本へ結び付けます。採用の仕組みについては[移管・採用契約](../../../16_TRANSFER_ADOPTION.md)を参照してください。形式が整ったJSONが存在するだけでは、現実と一致していることは保証されません。

最初の採用で必要なのは、実製品についての正確な最低限の情報です。いきなり将来の機能すべてを実装する必要はありません。後続の作業者が現状を理解できる、信頼できる出発点を作ります。

## 5. 最初の能力：会員の登録と一覧

Plannerは最初の実装能力を「許可された職員が会員を登録し、一覧で確認できる」と定義します。保存された会員が再起動後も残ること、識別番号が重複しないこと、権限のない利用者が登録できないことを含めます。オンライン決済と会費の記録はこのキャンペーンに含めません。

依存関係としてDBの保存先、会員のスキーマ、アクセス権、画面とAPIの接続が必要です。受け入れは、単に登録関数のユニットテストだけでなく、登録画面から保存し、一覧で再確認する利用者経路で評価します。

この目的、範囲、依存関係、担当者、受け入れ条件、失敗条件を一つの能力レベルのチャーターへまとめます。内部のファイル名や修正順序を一行ずつ指定する必要はありません。実装の技術的な自由度を残すことが、途中でバグが見つかったときの修正を容易にします。

認可されたら、I3 Execution Controllerが実装、統合、レビュー、修正、再試行、候補作成を引き受けます。CLIENTが一つ一つのテスト失敗を承認し直す必要はありません。ただし、製品の要求や外部行為の権限が変わる場合は、新たな判断が必要です。

## 6. 第一候補で起きる二つの問題

仮想的な最初の候補では、APIの登録処理は成功しました。しかし、保存直後に画面が更新されず、職員が登録結果を確認できませんでした。これは単体テストが緑でも、物理的な操作が不十分である例です。

I3はコードの現在の版を確認し、API応答、画面の状態更新、一覧の読み込みを調査します。修正後に統合テストと実際の画面操作を再実施します。元の会員登録能力の範囲内なので、新しいキャンペーンは不要です。

第二の問題として、同じ登録ボタンを二回押すと会員が重複して作成されました。画面だけの二重クリック防止で十分か、それともDB側にも一意制約が必要かを実装側が判断し、異常な再送にも耐えられることを検証します。既存会員が消えたり、他の職員が同時に操作して不整合を生む場合は、さらに原因を調査します。

修正候補ができたら、何のコード版・DB・設定でテストしたかを記録します。ユニット、統合、DB/currentness、意味、物理的な動作、人間による操作、公開準備という各検証層を区別します。試していない項目を合格と書くことはできません。

## 7. 利用者の確認と受け入れ

技術的な検証が成功した後、受付職員が実際の操作を試します。「入力して保存できるが、成功したことが分からない」という評価が出たとします。成功メッセージと画面表示の改善は、元の能力を実際に使えるものにするための作業です。

I3は同じキャンペーンで改善し、再確認を求めます。職員が必要な操作を完了でき、権限とデータ保存の確認が取れたら、CLIENTは最初の能力を受け入れられます。受け入れ記録には候補の識別、検証結果、残る制限、判断者を残します。

「会員登録と一覧が使える」という受け入れは、「会費が正しく計算される」「決済が安全に行われる」という保証ではありません。能力の境界を明示することで、次の作業の目的を正しく設定できます。

## 8. 二つ目の能力：会費を記録する

次にPlannerは「職員が会員の会費支払いを手動で記録し、未納状況を確認できる」という能力を検討します。これは第一の会員識別機能へ依存します。会員のIDが安定していなければ、誤った人へ支払い履歴が結び付く可能性があります。

利用者に、対象期間、金額の扱い、返金や取り消しの意味、退会者の記録、誰が修正できるかを確認します。実決済は含めないという境界を維持します。表現上「支払い済み」と表示されても、それは職員による入金記録であり、外部銀行や決済事業者の確定結果ではないことを明示します。

この能力のテストでは、同じ月の重複記録、誤った会員ID、取り消し、日付境界、権限、再起動後のデータ保持などを確認します。第一の能力で成功したテストを流用するだけでは、会費固有の意味を証明できません。

ここまで進んでも、クラブ管理の将来のすべての機能が完成したわけではありません。活動予約や分析レポートなどは、実際の需要が確認されたときに追加できます。小さな能力を確実に受け入れて積み重ねることが、誇大な完成宣言より持続的です。

## 9. 最後の復元演習

次の日に、別の担当者へリポジトリだけを渡すと想像してください。その担当者が確認すべき項目は次のとおりです。

1. 製品の現在の目的と、CLIENTが承認した範囲は何か。
2. 会員登録と一覧について、どの候補が受け入れられたか。
3. 会費記録の能力は未着手、進行中、受け入れ済みのどの状態か。
4. 現在のコード、DB、設定、検証結果はどこにあるか。
5. 未解決の問題と、その修正を担当するI3または関係者は誰か。
6. 実決済や外部公開など、まだ認可されていない行為は何か。

これらをチャットの全文を読むことなく説明できれば、継続性の基盤が実際に機能しています。答えが分からない場合は、参照元や正本が不十分かもしれません。未確認を隠さず、必要な事実を復元することで次の作業者が安全に再開できます。

最後に、比較の観点も忘れないでください。ArquitecturaRepoが単純なコーディングチャットより常に速いとは限りません。判断すべき指標は、実際に使える機能、変更時の混乱の少なさ、失敗からの復旧、新しい担当者への引き継ぎ、利用者が管理しなくてよい技術的負担です。長期間続く製品でその価値が示されるかを、実際のプロジェクトで測定してください。
