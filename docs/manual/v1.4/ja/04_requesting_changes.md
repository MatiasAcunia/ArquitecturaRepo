# 04 — 変更を依頼する方法

ArquitecturaRepo · 完全ユーザーマニュアル · v1.4版 · 日本語

> 利用者は、データベースのテーブル名やクラス構成を指定しなくても製品を方向付けられます。この章では、要求の意味を明確にし、必要な判断を行い、通常の不具合修正と新しい製品の要求を区別する方法を扱います。

## この章で学ぶこと

1. 実装方式より結果を伝える
2. 短い変更依頼の書き方
3. 利用者と技術担当の責任
4. 意見を変更した場合の履歴
5. 品質と使いやすさの要求
6. 優先順位と範囲
7. 判断が必要な質問
8. 実例と良くない依頼の改善

## 1. 最初に「何を可能にしたいか」を伝える

「会員一覧が重いので、データベースのインデックスを追加してください」という指示より、「会員が増えても検索結果が数秒以内に表示され、職員が作業を続けられるようにしたい」という依頼のほうが、製品の結果を明確にします。インデックスは一つの実装候補にすぎず、真の原因が画面側の無駄な読み込みなら最適な手段ではありません。

利用者が解決したい問題、誰が困っているか、どの状況で発生するか、どんな結果なら役に立つかを伝えてください。可能であれば具体例も添えます。たとえば「400人の会員から姓で探したい」「同姓同名が二人いる」「退会した人を誤って再登録したくない」などです。

技術担当は、その結果を実現するための設計、実装、テストを検討します。利用者がプログラミング経験を持っている場合は技術案を提案してもかまいません。ただし「この方法でなければならない」という契約にする前に、代替方法と費用・安全性を確認してください。

## 2. 短い変更依頼のひな型

必要な情報は一枚の簡単な説明から始められます。

| 項目 | 記入例 |
| --- | --- |
| 目的 | 会員を名前と識別番号で探せるようにする |
| 利用者 | 受付の職員 |
| 現在の困りごと | 一覧を手作業でスクロールするため時間がかかる |
| 期待する結果 | 入力すると対応する会員が見つかり、複数候補を識別できる |
| 重要な条件 | 許可のない利用者へ連絡先を表示しない |
| 初版では不要なこと | 複雑な統計、外部サービスとの自動同期 |
| 受け入れの例 | 二人の同姓同名会員が正しく区別される |
| 未決定 | 検索結果に退会済み会員を含めるか |

これは実装チャーターそのものではなく、製品の意図を伝える入口です。Plannerは現物のコードと要求を調べ、未決定事項を確認し、適切な能力単位へ整理します。依頼文に細かな技術指示を詰め込み、後から実装者が一字も変えられないようにする必要はありません。

「全部をきれいにして」と依頼する場合も、何を意味するかを追加すると有用です。たとえば「会員登録までの操作を三段階以内にする」「誤入力時に既存のフォームを失わない」「電話画面でもボタンが押しやすい」といった、確認可能な目標にします。操作感に関する要求は、コードの内部テストだけで判断しないことが重要です。

## 3. 利用者が決めるものと委任するもの

利用者が担当するのは製品の意図です。どの利用者がどんな操作を必要とし、何を最優先し、何に費用を払えるか、どの外部公開やデータ取り扱いを認めるかを決めます。社内規則や法律について判断権限を持たない場合は、該当する正式な責任者へ確認します。

内部の技術担当は、どう実現するかを引き受けます。Gitの衝突解消、技術構成、検証用環境、テスト、データ移行、ログや復旧の設計を、毎回利用者へ細分化して尋ねる必要はありません。重大な制約や費用が製品判断へ影響するときは、選択肢とその結果を分かる形で説明します。

I2 Plannerは製品の問題を実行可能な能力へ整理し、I3 Execution Controllerは認可された範囲で継続して実装します。I4は限定された実装や独立レビューを担えます。複数製品の統合と共有資源の判断が必要な場合はI1を設けることがあります。役割は責任の区分であり、必ず四つの個別AI会話を必要とするものではありません。

## 4. 意見を変えても履歴を壊さない

最初は「退会者を一覧から完全に削除する」と要求し、後から「以前の会費履歴は残したい」と考え直す場合があります。新しい明示的な製品決定は、以前の要求を置き換えることができます。しかし、過去の判断が一度存在した事実や、すでにその判断に基づいて作成したデータを消す必要はありません。

変更の前後を分かる形で記録します。いつ、どの範囲の要求が変化し、既存コードやDB、バックアップ、公開済みの操作にどんな影響があるかを調べます。実装済みの削除処理が、変更後の要求に反しているなら、必要な移行と安全な復旧の計画が必要です。

Product Stateと現在の要求は正本に反映し、古い設計案は履歴として参照します。二つの文書が共に「現在の決定」と主張すると、新しい担当者が誤った判断をします。たくさんの要約ファイルを増やすより、一つの明確な現在状態と参照可能な履歴を維持してください。

## 5. 品質に対する要求を明確にする

「動いているが見た目が弱い」「動作が遅い」「エラー時の説明が分かりにくい」は、正当な製品フィードバックです。利用者は、その体験を具体的な場面に結び付けて伝えられます。機能が存在するだけでは、使える製品としての受け入れが完成するとは限りません。

たとえばボタンが表示されない場合は、対象の画面、操作手順、端末・ブラウザの条件、スクリーンショットを提供します。これはデザインの好みではなく物理的な不具合です。表示はされているが目立たない場合は、人間による知覚評価の問題として扱います。実装側は両者の検証方法を分けます。

性能の要求も、試験条件なしでは曖昧になります。「会員500件の一覧が通常の職員端末で3秒以内」「低速な回線で操作不能にならない」といった条件が有用です。ただし数値は例示であり、実際の利用者や運用環境に合わせて決めてください。どの機能にも同じ測定値を強制する必要はありません。

## 6. 優先順位は実際の価値で決める

要望が十件集まったとき、十個のキャンペーンを同時に立ち上げることが最適とは限りません。今必要な利用者の操作、依存する機能、重大な欠陥、コスト、実施による干渉を考慮して順序を決めます。受付業務ができないなら、装飾的なレポートより会員検索の改善が先かもしれません。

まず一つの利用者経路を完成させ、それを確かめてから次へ進む方が効率的な場合があります。実装中のバグは元のキャンペーン内で処理します。Plannerが関与するのは新しい能力の戦略、認可範囲の変化、重要な新証拠、最終的な受け入れの判断です。

優先順位の変更も、今あるキャンペーンの成果や依存関係を確認して行います。以前の作業を無言で無効化すると、中途半端なマイグレーションやテスト用状態が残る可能性があります。中断する場合は、安全な停止点、再開に必要な情報、次の責任者を記録します。

## 7. 判断が本当に必要なとき

「使うDBをPostgreSQLにしますか、それともSQLiteにしますか」という問いは、一般には技術担当が要件から提案できます。一方、「会員の個人情報を外部のサービスへ送信してよいか」「本番の会費履歴を削除してよいか」「有料APIの費用を引き受けるか」は、適切な権限者の承認を必要とします。

判断が必要になった場合は、選択肢、具体的な利点と不利益、影響を受けるデータ、元に戻せるか、確認していない点をまとめます。利用者に毎回長いシステム設計会議を求める必要はありませんが、認可のない外部行為を作業者の判断だけで実行することもできません。

未確定の事項があっても、無関係なローカルテストやコード調査は継続できます。外部公開に関する承認がまだなくても、公開を伴わない画面の修正までは安全に進められる場合があります。停止するのは不確実性に依存する操作です。

## 8. 良い依頼の具体例

次の五つは、結果と境界を分けた依頼です。

1. 「職員が登録済み会員を名字と識別番号で探せるようにしたい。検索結果の連絡先は権限のある職員だけに表示してほしい。」
2. 「新規会員を保存した後、完了したことが分かる画面にしたい。入力エラーでは記入した内容を保持してほしい。」
3. 「会費が未納の会員を見たい。ただしこの段階では実際のオンライン決済を実行しない。」
4. 「スマートフォンでも登録画面を操作しやすくしたい。どのボタンが重要か職員と確認したい。」
5. 「既存の会員データを失わずに新しい形式へ移行したい。移行前に復旧可能なバックアップを用意したい。」

反対に「もっとプロらしく」「AIで全部自動化」「全部のエラーをなくす」とだけ書いても、完了を判断できません。Plannerは具体的な利用場面を聞き、検証可能な単位に分けます。利用者の要求は技術命令である必要はありませんが、解決したい問題が分かることは大切です。

技術的に完成した候補でも利用者が気に入らなければ、使い勝手や意味に関する具体的な不一致を伝えてください。元の能力に含まれる修正なら同じキャンペーンで改善できます。要求を大幅に広げる変更なら、別の製品判断として扱います。この区別が、継続的な実装と柔軟な製品設計を両立させます。
