# 02 — Plannerによる発見と正式な採用

ArquitecturaRepo · 完全ユーザーマニュアル · v1.4版 · 日本語

> 管理層が生成されたことと、その管理層が実際の製品を正しく表していることは別です。この章はHOLD / UNTRUSTED_CONTEXTから、検証可能な採用済みの基準点へ移るための利用者向け説明です。[採用契約](../../../16_TRANSFER_ADOPTION.md)と[製品発見の指示](../../../../prompts/PRODUCT_DISCOVERY_SESSION.md)を併せて参照してください。

## 1. チャットは製品の正本ではない

最初の対話では、利用者は大きな構想を説明します。たとえば「小さなクラブの会員を管理したい。会費も見たい」という発言から、Plannerは利用者や業務を理解するための質問を組み立てられます。しかし、その会話に書かれた内容をすべて現在の実装事実とみなすことはできません。

設計したい機能、実際に存在するコード、データベースの現在の状態、運用上の許可は異なる情報です。利用者が口頭で要求を変更した場合は、以前の製品要件を更新する必要があります。反対に、「コードは完全に動作する」とチャットで報告されても、その特定のコードに対するテストと実行結果を確認しなければ技術的な主張は成立しません。

そのため、導入後の最初の仕事はコードを作ることではなく、文脈を構築することです。Starter内のテンプレートには仮の状態が含まれます。誤って仮の値を採用すると、他人の製品名、コード参照、受け入れ履歴が正本に混ざり、後続の全担当者に誤った前提を与えます。未確認であることを示すHOLDは、隠すべき故障ではありません。

## 2. 作業領域を読み取り専用で準備する

まず実アプリケーションの正確なパスを指定します。Gitブランチ、未コミット変更、ソース構成、データベースや設定の位置、既存ドキュメント、テスト方法を読み取ります。作業者が自由に書き換えられる場所と、読み取りのみ許される場所を区別します。機密情報は画面やログへむやみに表示しないでください。

v1.4でインストールした管理層には、現状を調べるための操作があります。

    & "python" ".agentic-sdlc\tools\project_status.py" --control-root ".agentic-sdlc"
    & "python" ".agentic-sdlc\tools\discover_project.py" --project-root "."
    & "python" ".agentic-sdlc\tools\reconstruct_context.py" --root ".agentic-sdlc"

これらは状況を調べるための道具であり、製品の意味を自動的に発見する魔法ではありません。作業ツリーに多くの未コミット変更があるなら、誰の作業か、現在のキャンペーンに属するか、他の操作と衝突するかを記録します。Gitの更新時刻だけから担当者や承認を推測してはいけません。

環境により本番と開発用のデータベースが異なる場合は、接続先と対象スキーマを検証します。開発用に作成したサンプル行を、本番で承認された会員データとして扱ってはいけません。動いているサービスの設定を無断で変更することも禁止です。読み取り専用の探索の中で初めて、どの技術操作に追加の許可が必要かが明らかになります。

## 3. Plannerは製品を変える質問を優先する

Plannerが依頼者に尋ねる質問は、コードの細部を指定させるためのものではありません。製品の意味、対象ユーザー、業務上の例外、初版から除外する範囲を確定するためです。「バックエンドのサービスを何個にしますか」という質問より、「一人の会員が同時に二種類の活動へ参加することはありますか」という質問のほうが、要求の解釈を変えます。

クラブの例なら、次の点を最初に確認します。

| 質問 | 判断に関係すること |
| --- | --- |
| 誰が会員データを登録・閲覧できるか | 権限、画面、監査 |
| 同姓同名の会員をどう区別するか | IDと重複防止 |
| 会費の「支払い済み」は何を意味するか | 記録と実決済の境界 |
| 退会者の履歴を保存するか | 保存期間と削除規則 |
| ネット接続がないとき使うか | オフライン動作と同期 |
| 最初の版で不要な機能は何か | キャンペーンの範囲 |

依頼者が答えられない技術的な細部は、Plannerや実装担当が調査する対象です。一方、「誰が会員を削除してよいか」のような業務決定は、利用者の意図や正式な所有者の判断が必要です。回答がまだない場合は、推測して完了させず、明示的な未決定として管理します。

## 4. 要求、Product State、コードを一緒に見る

採用の準備では、少なくとも三種類の情報を整合させます。第一は、実際に確認された製品の目的と振る舞いです。第二は、その製品の現在の状態を表すProduct Stateや関連する管理記録です。第三は、ソースコード、設定、DB、テスト結果などの技術的な根拠です。

たとえば要求に「会員を登録できる」と書いていても、アプリのAPIが存在しないなら未実装です。APIが存在していても、重複したIDを拒否できないなら、まだ期待した能力に達していない可能性があります。コードに書かれているという理由だけで、利用者が望んだ仕様だと決めてはいけません。

Plannerは機能ごとに現在の境界、依存するデータ、利用者の期待、受け入れ方法を整理します。技術基準点には、参照するリポジトリとブランチ、正確なコード識別子、必要な状態の識別、既知の失敗条件を含めます。更新可能なCURRENT記録に古いSHAが残っていた場合、名前がCURRENTであることより物理的な照合結果を優先します。

最初からすべての要件を百ページに展開する必要はありません。採用前に必要なのは、真実の分かる基準点と、何が分かっていないかの記録です。大きな推測を一つの巨大な文書に固定してしまうと、後で修正するたびに資料が矛盾します。権限、可変状態、履歴、キャンペーンを適切な正本へ分離してください。

## 5. 採用とは現実へ接続すること

正式な採用では、スターターの形式を実際のアプリケーションの事実へ結び付けます。[導入契約](../../../16_TRANSFER_ADOPTION.md)は、この境界を説明しています。概略として、現状の読み取り、要件の確認、技術的基準点の検証、採用仕様の作成、権限や参照関係の事前点検、整合した状態の反映、再検証の順になります。

作業者が不明なコミットを適当に記入したり、テンプレートにある架空の合格記録を残したりしてはいけません。依頼者による確認が必要な決定は依頼者へ戻し、技術的な不確実性は適切な担当者が調べます。互いに矛盾する参照、確かめていない本番DB、実在しない成果物を持つ採用仕様は、表面的に整ったJSONでも採用すべきではありません。

アプリケーションがすでに管理されている場合は、新規導入の考え方を適用せず、[既存プロジェクト接続の事前点検](../../../32_EXISTING_GOVERNED_ATTACHMENT.md)を使います。過去のキャンペーン、履歴、所有権、現在のDB基準点を維持しながら接続を評価するためです。古い管理層を削除して作り直すことは、採用ではありません。

採用の結果は「管理層が実際のプロジェクトを参照できるようになった」という状態です。そこから先に、各機能が正しく実装される工程が始まります。採用済みの記録と完成済みの機能を同じ成功表示へまとめないでください。

## 6. 新しい文脈で復元できるかを試す

本当に引き継ぎ可能かどうかは、以前のチャットを知らない担当者を想定したときに分かります。その担当者は、現在の要求、実装された能力、活動中のキャンペーン、変更可能な範囲、重要な証拠、次の担当者を現物から特定できるでしょうか。

reconstruct_contextで形式的な復元を試み、その結果が実際のリポジトリと矛盾しないか確認します。問題が見つかった場合は、テストを迂回するのではなく、参照の欠落、情報の古さ、権限の不一致、DB状態の不明などを分類します。ある機能に必要な情報が復元できなければ、その機能についてはHOLDとして扱い、影響しない安全な調査は続けられます。

「引き継げる」とは、別のチャットが記憶しているという意味ではありません。現時点のコード参照と明示的な採用記録から作業の正当性を再構成できることです。これは、単純な会話による開発と比較するときの重要な評価項目です。

## 7. 最初のキャンペーンを認可する

採用後、Plannerは価値のある最小の能力を選びます。大きな製品を一度に完成させる必要はありません。会員管理アプリなら、会員の登録と閲覧を最初の能力とし、会費と決済は次へ回すことができます。能力単位のチャーターには目的、境界、依存関係、担当者、受け入れ条件、失敗条件を記載します。

認可される前は、Plannerの考察や試作品を本番実装の権限と混同してはいけません。認可後はI3 Execution Controllerが、同じ範囲の実装、デバッグ、テスト、レビュー、再試行、復旧を一貫して担当します。一つのバグが出るたびにPlannerへ戻して別キャンペーンを作るのは、作業の連続性を損ないます。

戦略を再検討するのは、製品の目的が変わった場合、認可範囲を超える行為が必要な場合、または既存の計画を無効にする重要な証拠が現れた場合です。通常のテスト失敗と、チャーターそのものの無効化は別です。依頼者は製品の意図と受け入れに集中し、内部の技術的な再試行を監督し続ける必要はありません。

## 8. 会員管理システムの初回セッション

最初の相談で利用者が「職員が会員を登録できるようにしたい」と言ったとします。Plannerは実際のコードを調べ、現状では会員テーブルは存在するが編集画面がなく、登録用APIも途中までしかないことを確認します。この結果は推測ではなく、対象のコードとDBスキーマへ参照を結んで記録します。

次に、会員に必要な項目、重複検出、アクセス権、削除の意味を利用者へ確認します。初版では氏名、連絡先、活動区分だけを扱い、実決済は行わないと決めたとします。Plannerはこの境界を記録し、会員登録・表示・入力検証を一つの能力として定義できます。

実装側には「登録の完了後に一覧で会員を確認できる」「同じ識別子を二重登録できない」「許可されない利用者は登録できない」「エラー後も既存会員は失われない」などの受け入れ条件が渡ります。どのクラスで実装するか、内部で何回修正するかは担当技術者が決めます。

完了報告には、変更したコードへの参照、使用したテスト、起動した環境、残る不確実性を含めます。利用者が実際に画面を試して「登録はできるが、確認操作が分かりにくい」と言った場合は、人間の使い勝手の問題として同じ目的の中で改善します。単にユニットテストが緑だから受け入れるのではありません。

最後に、新しい担当者へ同じリポジトリを渡す想定で再構成を確認します。どの能力が受け入れられ、会費処理がまだ対象外なのか、現在のコードの識別と共に読み取れれば、初回採用は実務的な意味を持ちます。
