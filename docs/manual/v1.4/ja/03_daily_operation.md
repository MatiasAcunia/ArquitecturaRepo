# 03 — 日常運用と継続的な実装

ArquitecturaRepo · 完全ユーザーマニュアル · v1.4版 · 日本語

> ここでは、製品の基準点が採用され、作業の権限と目的が明確になった後の一日を説明します。通常のバグ修正を何度も戦略会議へ戻さず、実際の成果と証拠を積み重ねることが中心です。[権限モデル](../../../../protocols/AUTHORITY_MODEL.md)と[運用プロトコル](../../../23_OPERATIONAL_AGENTIC_SDLC_V1_2.md)の適用範囲を確認してください。

## この章で学ぶこと

1. 新しいセッションで確認するもの
2. 目的を検証可能な能力に変える
3. I3が受け持つ一連の作業
4. 外部行為に必要な許可
5. 実装報告を評価する
6. Gitと現在性
7. 一日の終了条件
8. 会員管理の運用例

## 1. 昨日のチャットを覚えている必要はない

新しいセッションの最初に、担当者は現在のリポジトリ、対象ブランチ、変更中のファイル、採用済みのProduct State、認可されたチャーター、活動中の実行状態を確認します。チャットの以前の報告は手掛かりですが、古いコードや異なる環境を指している可能性があります。

「前回はすべて成功したらしい」という記憶を根拠に、直ちに製品を公開してはいけません。実際の実行候補がどのコミットと設定から構成され、どのデータベースに接続し、どの検証を受けたかが必要です。別の作業者が未コミットの変更を残している場合は、所有者と干渉リスクを把握します。Gitが進んでいることだけでは、作業の担当者やキャンペーンを証明できません。

現在の情報が矛盾する場合は、影響のある変更を止めて事実を調べます。影響しない作業についてまで、無期限に全体を停止する必要はありません。重要なのは、何を安全に継続できるかを根拠に基づいて区別することです。

## 2. 願望を能力に変換する

依頼者の希望は、必ずしも実装単位になっていません。「会員管理を簡単にしたい」という希望には、入力画面、検索、既存データの移行、権限、操作手順などが含まれる場合があります。Plannerは目的を聞き、最初の結果を試せる能力へまとめます。

たとえば「職員が会員を登録できる」という能力なら、許可された職員が必要項目を入力し、保存結果を一覧で確認できることを定義します。重複した識別子や無効な入力を拒否すること、予期しないエラーで既存会員を失わないことも重要です。実決済や会計帳票は対象外と明記できます。

チャーターは、なぜ必要か、どこまで実装するか、どの部分に依存するか、誰が担当するか、何をもって受け入れるか、どんな結果なら不合格かを説明します。クラス名を一つ一つ指定する必要はありません。内部設計とコード変更の裁量をI3へ委ねることで、バグが見つかるたびにチャーターを書き直す混乱を防ぎます。

## 3. I3は途中の失敗も引き受ける

認可後のI3 Execution Controllerは、実装だけでなく、検証、デバッグ、レビュー、失敗した試行の再実行、必要な内部リファクタリング、復旧、次の候補の統合まで連続して担当します。通常のテスト失敗を「Plannerに戻して新しいGoalを作ってください」と依頼者へ押し返してはいけません。

実装者が構文エラーを出した場合、該当するコードを修正して再テストします。DBのマイグレーションが失敗した場合、元のデータを保護し、影響範囲と復旧方法を検証します。レビューで同じクラスの問題が二度以上繰り返された場合、局所修正を延々と追加するのではなく、該当サブシステムを体系的に点検し、独立した確認まで実施する必要があります。

もちろん、I3があらゆる判断を独占するわけではありません。実装中に「会費を実際の決済事業者へ送信したい」という新要求が現れれば、元の単純な記録機能から外れます。新しいセキュリティ、費用、個人情報、外部契約の判断を必要とするため、権限者とPlannerによる再検討が適切です。失敗と範囲変更の違いを記録してください。

## 4. 外部行為には境界を設ける

読み取り専用のコード調査、ローカルテスト、許可済みのファイル修正と、外部公開、第三者へのデータ送信、費用を発生させるAPI呼び出し、運用DBの変更は同じ行為ではありません。後者については、目的、対象、費用・回数、復旧可能性を明確にした承認が必要です。

「GitHubに接続できた」「デプロイ用キーが環境にある」という事実は、そのキーを使って本番サービスを変更する許可ではありません。シークレットを課題の説明文やログに埋め込まず、必要な権限を最小化します。外部のAIモデルを追加するかどうかも製品上の選択であり、ArquitecturaRepoが自動的に要求するものではありません。

手元のデータを使うサンプルと本物の会員データには異なる保護が必要です。デモ用データが合成であれば、その事実を明記します。操作画面に顧客の電話番号が表示されるなら、スクリーンショット、テストログ、問題報告へ不用意に含めないようにします。

## 5. 完了報告は「PASS」という一語では足りない

I3から候補完成の報告が届いたら、何ができるようになったかをまず確認します。変更したファイル数やテスト件数は参考情報ですが、機能の品質そのものではありません。特定の受け入れ条件をどの証拠で満たしたかを確認します。

| 検証の層 | 主な質問 |
| --- | --- |
| Unit | 個々の関数は期待どおりか |
| Integration | API、DB、画面などが一緒に動くか |
| DB / Currentness | テスト対象は現在のスキーマと正確な状態か |
| Semantic | 実際の要求や例外に意味が合っているか |
| Physical | 実環境で起動し、操作が成立するか |
| Perceptual / Human | 利用者にとって理解しやすく、役に立つか |
| Release | 公開対象と権限、配布物の識別が正しいか |

単体テストが100個成功しても、UIが白いままなら実際の利用者の操作能力は未確認です。反対に、細かな警告が一つ残っているだけで、受け入れ可能な機能を無限に保留することも避けます。どの失敗が受け入れを妨げるかを、チャーターの目的に結び付けて判断します。

## 6. Gitは継続性の材料であって権限ではない

コミットは変更内容を参照する有用な手段ですが、「誰が承認したか」「何のための変更か」「現在のDBに対応しているか」を単独で答えません。リポジトリの管理記録、チャーター、テスト結果、DBの参照、成果物の識別が必要です。複数のブランチを並行して動かす場合は、同じ設定ファイルや同じデータベースへ干渉しないか評価します。

不要なクローンや重複した成果物を増やさないことも重要です。通常は一つの正本チェックアウトを利用し、並行作業の理由がある場合のみ一時的なworktreeを使います。レンダリング出力、大容量キャッシュ、テスト用動画などは、後で必要な正本証拠でない限り、一時領域や無視設定の下に置きます。

復旧可能な変更を優先してください。作業者が間違えたからといって、未確認のファイルを一括削除したり、ユーザーの変更を強制的に消したりしてはいけません。復旧操作にも対象の確認と権限が必要です。

## 7. 一日の終わりに答える五つの質問

作業終了時には次の五つを残すと、新しい担当者が状況をつかめます。

1. 何の製品能力が実際に増えたか。
2. その結果を証明する正確なコード・データ・成果物はどれか。
3. どの品質ゲートが成功し、どれが未検証か。
4. 未解決事項の責任者は誰で、元のキャンペーンで続けられるか。
5. 次の作業者はチャットなしでどの記録から再開できるか。

「コミットした」「AIが完了と答えた」「何時間動かした」だけでは不十分です。利用者が新しく試せる機能があるか、障害の可能性が減ったか、古い情報への依存が解消したかという結果を示します。

## 8. 仮想クラブでの一日の流れ

午前中、Controllerは会員登録キャンペーンの現在の状態を読み取ります。昨日の候補では登録後の画面更新が失敗し、APIとDBのテストは成功していたとします。まず候補のコード識別、ログ、再現条件を調べ、画面が古い一覧データを保持する原因を見つけます。

修正は元の登録能力の範囲に収まるため、新しいPlannerキャンペーンは不要です。実装担当は表示更新を修正し、単体・統合・ブラウザ操作の三種類を再検証します。会員データの永続性も確認し、同じ候補の技術結果と画面の証拠を記録します。

夕方に利用者が画面を試し、「登録ボタンは目立つが、保存後に何が起きたか分かりにくい」と伝えたとします。これは製品の意味に直結する人間による評価です。既存の目的の中で成功メッセージや表示を改善できるなら、I3が同じキャンペーンで修正します。利用者が「会員証を郵送する機能も追加して」と要求したら、外部の個人情報と費用を伴う別の範囲として検討します。

最後に、実際に確認した候補、残る課題、次の担当者へのルートを正本へ保存します。翌日に別のチャットが開始されても、一から事情を説明し直す必要がない状態が日常運用の目標です。
