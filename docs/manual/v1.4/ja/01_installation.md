# 01 — インストールと初期設定

ArquitecturaRepo · 完全ユーザーマニュアル · v1.4版 · 日本語

## 1. インストールに必要な環境と権限

以下ではWindowsとPowerShellを例にします。Python、Git、ソースファイルへアクセスできるローカルディレクトリを用意してください。v1.4のポータブルCIではPython 3.12を使用しています。ただし特定のクラウド会社やコーディングモデルを契約する必要はありません。チャットやプログラミングエージェントは補助的な操作方法であり、実行対象と権限は別に確認します。

PowerShellで次のように現在の環境を確認できます。

    & "python" --version
    & "git" --version
    Get-Location

コマンドが失敗した場合、端末のPATHとインタープリタを確認してください。必要なPythonパッケージは、配布物に明示された要件ファイルから導入します。無関係なインストーラを実行したり、エラーを隠すために検証コードを書き換えたりしないでください。導入の責任者は対象フォルダへ書き込める必要がありますが、外部公開、課金、機密情報の送信まで許可されているとは限りません。

最初の一歩で最も重要なのは、どのディレクトリを扱っているかという事実です。スターターのREADMEを開いたつもりで、自分のアプリケーションへ変更を加えることもあれば、反対にアプリケーションを変更したいのにスターターそのものを書き換えてしまう場合もあります。作業を始める前に、Gitリポジトリ名、現在のブランチ、未コミットの変更、書き込み可能な範囲を記録してください。

## 2. スターターとアプリケーションは別のもの

ArquitecturaRepoはプロトコル、プロファイル、テンプレート、検証ツールを配布する元のリポジトリです。一方、会員管理サービスや店舗向け予約アプリなどの実製品は、独立したアプリケーションリポジトリに置きます。自分用のスターターを保守する場合はforkを作成できますが、forkしただけで製品は作られません。

たとえば、次の構成は役割を分離しています。

    C:\Proyectos\
        ArquitecturaRepo\
        club-app\

前者のフォルダからセットアップツールを実行し、後者のフォルダに管理層を導入します。スターターの合成サンプルを実製品の現在状態としてコピーしてはいけません。サンプル内の要求、所有者、テスト成功、データベース参照は説明用であり、実際のアプリについて確認した事実ではありません。

取得したスターターの版も記録します。固定された[GitHub v1.4.0リリース](https://github.com/MatiasAcunia/ArquitecturaRepo/releases/tag/v1.4.0)には配布用ZIP、チェックサム、マニフェストがあります。現在のmainブランチで更新されたドキュメントが、以前のリリースZIPに自動的に含まれることはありません。元のコード、配布物、追加文書を混同しないことが、後の再現性とサポートの基本です。

## 3. 導入前に対象を確認する

スターター側から作業する前に、実際のアプリケーションを読み取り専用で点検します。Gitの状態とディレクトリが一致するか、すでにアプリのコードやデータが存在するか、以前のエージェントが作ったファイルがないかを調べます。既存の管理層 .agentic-sdlc/ がある場合は通常の新規生成を実行しません。

既存アプリにデータベース、移行履歴、稼働中のサービスがあるとき、初回導入と運用中の継承ではリスクが異なります。特に既存のProduct Stateをテンプレートで置き換えると、承認済みの決定と現在の技術証拠が失われます。その場合は[既存の管理済みアプリケーション向け手順](../../../32_EXISTING_GOVERNED_ATTACHMENT.md)から始め、書き込みを伴わない事前点検を優先してください。

何もない新規製品でも、どのユーザーを想定するか、扱うデータ、初版の範囲、費用やライセンスの制約は簡単に書き出します。後続のPlannerが質問を絞り込みやすくなります。ただし、この時点では未回答の項目を勝手に決めたことにせず、不明事項として残します。

## 4. 六つのプロファイルを選ぶ

プロファイルは製品のリスクと運用形態で選びます。名称や条件の正本は[profiles/profiles.json](../../../../profiles/profiles.json)です。

| プロファイル | 主な適用状況 |
| --- | --- |
| SMALL | 単純な製品で、重い状態管理や運用制御が不要 |
| STATEFUL | 永続データ、ユーザー、バックアップ、スキーマ変更が重要 |
| ARTIFACT_HEAVY | 多数の成果物、保存費用、由来、権利が重要 |
| MULTI_WORKSTREAM | 複数の開発領域が一つの製品を完成させる |
| MULTI_PRODUCT | 複数製品が資源や運用方針を共有する |
| HIGH_CONSEQUENCE | プライバシー、安全性、資金、重大な不可逆操作を伴う |

担当AIの人数を増やしたいという理由だけでMULTI_PRODUCTを選ぶ必要はありません。小さな試作であればSMALLを起点にできます。会員情報と会費を保持する実例ならSTATEFULを検討します。後で観測された要求が変化した場合は、プロファイル選択の根拠を更新してください。プロファイルがあること自体は、対象アプリケーションが安全であることの証明になりません。

## 5. 新規プロジェクトに管理層を生成する

対象を確認したら、スターターのルートから次のコマンドを実行します。これは新しいプロジェクトを例にしたコマンドであり、既存の管理層を持つアプリケーションにそのまま適用しないでください。

    & "python" "tools\scaffold_project.py" --target "..\mi-proyecto" --profile "SMALL" --product-id "MI_PROYECTO" --objective "Initial objective, awaiting confirmation" --language "en" --no-feedback-workflow

会員管理アプリの想定例では、製品の状態を持つという事実に合わせて次のようにします。

    & "python" "tools\scaffold_project.py" --target "..\club-app" --profile "STATEFUL" --product-id "CLUB_MANAGER" --objective "Member and dues management for a club" --language "en" --no-feedback-workflow

パス、ID、目的は実例の値に置き換える必要があります。コマンドの言語指定は生成物の設定であり、この日本語版マニュアルの表示言語とは別です。現実の環境でサポートされる言語やオプションは、実行中のスクリプトのヘルプで確認します。

成功すると、対象のリポジトリに .agentic-sdlc/ が作成されます。通常のアプリケーションのソースを置き換えるコマンドではありません。初期状態が HOLD / UNTRUSTED_CONTEXT となっているのは、まだ実製品の要求、コード基準、権限、受け入れを確認していないからです。設定ファイルのステータスだけをREADYへ変えることは、導入成功の証明ではなく誤った状態の宣言です。

オプションの --with-runtime はローカルのキャンペーン制御に関する参考機構を加えますが、外部のAIモデルを導入したり、Codexのネイティブ実行を開始したり、課金を認めたりしません。--no-feedback-workflow は定期的なGitHub Actionsのスケジューラを無効化しますが、ローカルのメタデータレポート生成器とは別の設定です。

## 6. 導入結果を検証する

生成が成功したら、実製品のディレクトリで検証用依存関係と読み取り系のチェックを実行します。

    & "python" -m pip install -r ".agentic-sdlc\requirements-validation.txt"
    & "python" ".agentic-sdlc\tools\project_status.py" --control-root ".agentic-sdlc"
    & "python" ".agentic-sdlc\tools\discover_project.py" --project-root "."
    & "python" ".agentic-sdlc\tools\reconstruct_context.py" --root ".agentic-sdlc"

project_statusは管理状態と不足事項を表示します。discover_projectは実際のファイルを調査し、reconstruct_contextは新しい担当者が現状を再構成できるか確かめます。これらがHOLDを返しても、未確認の製品情報を捏造していないという点で正しい場合があります。すべての構文チェックが成功しても、利用者の要求に沿ったアプリの能力を証明するわけではありません。

確認項目は三つです。正しいディレクトリに管理層が存在すること、既存のコードやワークフローが保存されていること、現在の未確認事項が読み取れることです。実際の製品についての探索、要件の承認、技術基準の採用は次章で扱います。インストール、採用、実装、受け入れの四つの結果は区別してください。

## 7. 既存の管理済みプロジェクトには別の手順がある

再度コマンドを実行する前に、.agentic-sdlc/ の内容を調べます。既存のCURRENT、権限記録、活動中のキャンペーン、実行リース、DBの参照、成果物の由来は復旧に必要な正本である可能性があります。強制削除や上書きは、標準的な問題解決方法にしてはいけません。

古いバージョンで構築したプロジェクトに新しい版を導入する場合も、互換性を憶測して移行しないでください。[アップグレード条件](../../../47_V1_4_RELEASE_NOTES_AND_UPGRADE.md)と[既存プロジェクトの安全な接続](../../../32_EXISTING_GOVERNED_ATTACHMENT.md)を確認し、移行対象と残すデータを明確にします。サンプルを生成し直すより、既存の基準点を尊重することが重要です。

## 8. 失敗した場合の判断

| 現象 | 起こり得る原因 | 安全な次の行動 |
| --- | --- | --- |
| Pythonが認識されない | インストールまたはPATHの問題 | 環境を修正し、コードや状態は変更しない |
| 管理層が見つからない | 対象パスの違い、生成失敗 | 実行ログと作業ディレクトリを確認 |
| 既存の管理層がある | 実製品がすでに管理されている | 新規生成をやめ、読み取り専用の接続点検へ |
| jsonschemaがない | 宣言済み依存が未導入 | 対応する要件ファイルから追加 |
| UNTRUSTED_CONTEXT | 実製品の事実がまだ採用されていない | Product Stateと要求の探索を続ける |
| コーディングツールが別のrepoを見る | 作業領域の設定が異なる | 書き込みを止め、対象と権限を確認 |
| テストは緑だがアプリが動かない | 管理機構の検査と実製品の実行は別 | 実際の起動・画面・データ操作を試す |

作業後に「何を生成したか」「どこに生成したか」「何をまだ確認していないか」を記録してください。別の担当者がその三点を実データと照合できれば、次の採用作業に進むための出発点になります。失敗した検証を削除して成功したように見せる必要はありません。
