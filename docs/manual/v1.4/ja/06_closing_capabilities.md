# 06 — 能力の受け入れと作業の終了

ArquitecturaRepo · 完全ユーザーマニュアル · v1.4版 · 日本語

> 技術的な作業の終了と製品能力の受け入れは同じではありません。この章は、何を実際に確認すれば「完成」と言えるのか、何を同じキャンペーンへ差し戻すのか、いつ新しい判断が必要なのかを整理します。

## この章で学ぶこと

1. 能力とは利用者にとっての結果
2. 終了の五つの要素
3. 一つの候補と一連の証拠
4. 不足する証拠の扱い
5. 受け入れ、差し戻し、目的変更
6. 繰り返す確認と停止条件
7. 受け入れ記録を正本に残す
8. 会員登録の判断例

## 1. 「機能を作った」だけでは能力にならない

利用者が「職員が会員を登録できるようにしたい」と希望した場合、実装者が登録用の関数を書いただけでは能力の受け入れは成立しません。正しい権限を持つ職員が画面から入力し、保存された会員を確認でき、失敗時にもデータが破壊されないことなど、製品として意味のある結果が必要です。

内部の成果には価値があります。ソースコードが整理され、テストが増え、重複処理が削減されることは保守性を改善します。しかし受け入れ判断では、それらがどの利用者経路や危険の低減を支えているかを確認します。「コミットが30個」「エージェントが20時間作業した」という数字を、製品能力が増えた証拠として使わないでください。

機能は小さくてもかまいません。会員登録だけを完了し、会費計算やオンライン決済を後に回すことは合理的です。むしろ、最初からすべてを完成したように見せかけると、何が現実に使用でき、何が未実装なのか利用者が判断できません。

## 2. 終了を五つの要素で考える

最終的な評価では、少なくとも五つの観点をそろえます。

| 観点 | 確認事項 |
| --- | --- |
| 目的 | 認可された要求と結果が一致しているか |
| 候補 | どのコード、設定、DB、成果物の組み合わせか |
| 証拠 | 適切な検証が実行されたか |
| 人間による判断 | 必要な使いやすさや知覚品質を確認したか |
| 継続性 | 受け入れ結果と残りの問題を正本から復元できるか |

構文テスト、統合テスト、DB/currentness、意味、物理的な動作、人間の評価、公開の準備は、別々のゲートです。要求がデータの保存に関係する場合はDBの確認を省略できません。実際の画面を使う製品なら、ユニットテストだけで画面の受け入れを完了したことにもできません。

同時に、あらゆるプロジェクトへ同一の大規模な評価儀式を強制するべきでもありません。小さなCLIツールに、人間の視覚的デザイン審査が必要とは限りません。必要なゲートは、能力の目的とリスクに比例して定義します。重要なゲートが未検証なら、その部分を未確認として扱います。

## 3. 正確な候補を確認する

同じ機能を何度も修正すると、過去のテストが現在のコードに対して有効か分からなくなります。受け入れ対象には、少なくともコード版、必要な設定、データとスキーマの識別、実行環境、関連する成果物を結び付けます。

「昨日のV3では画面が動いた」という報告だけでは、今日のV4を受け入れることはできません。V4で変えた場所が画面以外であっても、依存関係が変われば物理的な動作が異なる可能性があります。再実行が必要な検証範囲を明確にし、古い結果を無断で引き継がないでください。

ソースコードのハッシュは重要ですが、それだけで本番のデータベース、外部設定、利用者の権限を固定できません。必要な情報を一つの候補に関連付けて、受け入れ判断の対象を特定します。成果物を再生成した場合も、古い画像や動画のハッシュを新しい候補に流用しないようにします。

## 4. 証拠が足りないときは作業を区別する

ある候補のユニットテストは合格しているが、実環境で会員登録ができるか未確認という場合、正しい判断は「ユニット検証済み、物理的動作未確認」です。未確認の部分をPASSへ変更してはいけません。

不足している証拠が元の能力に含まれるなら、I3は同じキャンペーンでテストや評価を追加できます。必要な検査のために新キャンペーン、新Goal、新しいPlannerの戦略パスを必ず作る必要はありません。差し戻しでは、どの条件が満たされていないかを具体的にまとめます。

逆に、ユーザーが突然実決済を要求した場合は、単なるテスト追加ではありません。元の会費記録に比べ、外部資金、契約、セキュリティ、復旧方法の意味が変わります。認可範囲の外へ進む前に、必要な製品判断と新しい境界を確認します。

証拠が見つからないことと、必ず不具合があることも別です。テスト結果が保存されていない場合は、そのテストが失敗したと断定できません。未実施・記録欠落・実際の不合格を分け、必要な検証を合理的な範囲で実施します。

## 5. 三つの最終判断

一つ目は「受け入れ」です。定義された能力を利用者が実際に使え、必要な品質・リスク条件を満たし、候補と証拠が再構成可能なときに適用します。残る軽微な改善は後続の作業へ回すこともできますが、受け入れ条件に関係する欠陥を隠してはいけません。

二つ目は「同じ範囲で修正」です。機能の目的は変わらず、具体的なバグ、統合失敗、性能不良、画面の使いにくさなどが残る場合です。I3にまとめた失敗条件を返し、同じキャンペーンで修正、再検証、独立レビューを進めます。差し戻しのたびに新しい戦略計画を起こす必要はありません。

三つ目は「目的の再定義」です。利用者の要求そのものが変わる、技術的制約が当初の境界を無効にする、重大な新事実により受け入れ条件が適切でなくなる場合です。そのときはI2 Plannerや必要な権限者が、変更した目的と依存関係を整理します。

## 6. 終わりのない検査を避ける

品質は重要ですが、受け入れ可能な能力を無期限に保留するのは別の問題です。受け入れに関係する失敗条件がなくなり、重要な品質ゲートが満たされ、残るリスクを権限者が理解しているなら、終了できます。

反対に、同じ種類の不具合が何度も繰り返されるのに、細かな修正を毎回「最終版」と呼ぶべきでもありません。そのサブシステムを深く検証して原因を解消し、独立レビューで確認します。正しい停止条件は、資料やテストの数ではなく、能力のリスクと受け入れ条件で決まります。

「すべての可能な環境で完全に安全」という証明は、通常は現実的ではありません。試したOS、端末、入力条件、データ量を正確に記録し、試していない条件を区別してください。必要なら公開を段階的に行い、復旧可能性を維持します。

## 7. 受け入れ記録は新しいチャットでも読めるようにする

最終判断をチャットの一言にだけ残してはいけません。正本には、対象能力、認可されたチャーター、採用した候補の識別、検証の証拠、判断者、残るリスク、次のルートを保存します。どこが現在の状態で、どこが履歴なのか明確にします。

新しい担当者が、既に受け入れられた会員登録機能を誤って最初から作り直したら、運用の継続性は保たれていません。逆に未検証の会費機能を、過去のキャンペーンのPASSから推測して公開するのも危険です。各能力の範囲と現在性を分離することで、後続作業が安全になります。

完成した機能に新しい要求を追加する場合も、元の受け入れ記録を書き換えて過去をなかったことにしません。受け入れ済みの版と、その後の変更要求を追跡可能にすることで、問題発生時にどの段階から修正すべきかを判断できます。

## 8. 会員登録の判断例

仮想クラブで、会員登録のフォームが完成したとします。ユニットテストは成功し、DBへの保存も確認されています。しかし受付担当が実際に使うと、保存ボタンを二回押したときに同じ会員が重複登録される問題が見つかりました。

この場合、製品能力はまだ受け入れられません。I3は元のキャンペーンで二重送信対策と重複防止を修正し、同じ入力と別の入力を使った統合テスト、実際のフォーム操作、DBの一意性を検証します。すべてを新キャンペーンへ移し替える必要はありません。

次の候補では重複が防止され、登録結果が明確に表示され、許可のない利用者は登録できないと確認できました。利用者も実際の操作を試し、初版に必要な流れを承認しました。証拠と版の識別が残っていれば、この能力を受け入れて次の会費記録へ進めます。

ただし、オンライン決済までは受け入れていません。会員登録が完成したからといって、支払いを実行できる、金銭を安全に扱えると主張するのは誤りです。次の能力は、別の目的、依存関係、受け入れ基準を持つ必要があります。
