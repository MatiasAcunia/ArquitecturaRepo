# v1.2 Stabilization Master Plan

Status: strategic stabilization plan, NOT acceptance or release authorization. The one machine-readable release-gate owner is \`state/V1_2_ACCEPTANCE_CRITERIA.json\`. Stable \`main\` remains 1.1.0 until exact-candidate independent review and user authorization.

## Mission and stopping condition

Ship a trustworthy first-use public starter, not an endlessly expanding agent ecosystem. Core expectations: no accidental loss of existing project state; one canonical owner per truth/identity; correct Goal/Planner/I3 boundaries and fresh-context reconstruction; validated rollback; bounded privacy/cost; enough useful documentation that an unrelated adopter can start correctly; transparent differentiation between actual support, simulated tests, experimental adapters and physical human acceptance.

Do not alter active productive other existing production Goals, repos, private SQLite, media, cloud resources, licensing decisions or scheduled tasks. A sandbox can be deleted only after the evidence has been captured and the tester has identified its ownership. One v1.2 PR and coherent commits; no branches or campaigns per bug.

## PASS1 — whole-product reconstruction and critical path

The user journey: README -> first-run platform/profile choice -> discovery -> CLIENT theory and Product State -> canonical technical baseline and authority -> I2 charter -> persistent I3 Goal/Plan -> real code/artifact state -> reviewer and external effects -> acceptance -> installation/maintenance -> anonymized feedback.

Separate **four kinds of proof**, none substituting for another:
1. Code CI: covered scripts on an exact commit.
2. Local physical continuity: real app/DB, restart, multiple actual invocations and a successful bounded recovery.
3. Provider/host/scheduler/receiver: independently bound physical readback of an external effect or API with cost/privacy authority.
4. Human/product decision: explicit CLIENT acceptance and release/publication approval.

Release-critical route: preserve existing state -> obtain CRUD longitudinal terminal -> resolve systemic starter defects -> adopt a governed existing repo on a disposable copy -> independent clean-install and security challenge -> one exact-head regression -> independently authorize a declared feature set -> release. No "first video demo" before the public instructions have been followed from a clean environment.

This PASS3 is justified by materially new evidence about systemic path/state/installation boundaries, not ordinary in-charter bugs. Reuse existing owners and avoid creating another control plane.
